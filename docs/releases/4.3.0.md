# Sans Password Manager 4.3.0

A show/hide control on every password box, and the answer to the roadmap's
question about hardware-backed release signing.

## Show what you are typing

Every password input in web mode now has an eye beside it: the login form, all
three fields of the master-password change, and the Bitwarden export password.

One helper renders them all, so a password box added later cannot quietly ship
without one — the regression suite counts the inputs on the served pages and
fails if any lacks a control.

The state never persists. Every page load starts masked, because a field that
remembered "shown" would eventually be shown at the wrong moment. Revealing
also restarts the idle lock: looking at your password is activity, and it
should not be the moment the timer decides nothing has happened.

### The RTL bug, again

In an Arabic page the control landed **on top of the caret**.

A password field keeps left-to-right content in a right-to-left page — that
rule has been there since 3.13.0, because a password laid out RTL puts the
caret on the wrong end. So its text begins on the left. The wrapper around it
was still RTL, which put the button's inline end on the left as well: directly
over the first characters typed.

This is the Arabic search icon of 3.13.0 happening a second time, in a
different element, and it was again invisible to every assertion and obvious
the moment the page was rendered in Arabic. The wrapper now follows its field.

## Hardware-backed release signing: the answer is no, and here is what to do
   instead

The roadmap asked whether release provenance could be tied to a key a person
holds rather than to a workflow in a repository.

**Hardware in CI: no.** The artifact is built by the release workflow from the
tag, and a GitHub-hosted runner exposes no TPM and no smartcard. A self-hosted
runner with a token in it would work, and would put a maintainer-operated
machine in the release path — the shape this project avoids everywhere else.

**Building locally and uploading: no.** That moves the published bytes outside
the workflow the attestation describes, trading a stronger claim about *who*
for a weaker one about *what*.

**What is already reachable.** Because 3.9.0 made the archive reproducible, a
maintainer holding a token can rebuild the published archive byte for byte and
sign that, after the fact, with the build staying where it is. Signing the tag
with a hardware-held key is reachable today as well. Neither needs anything in
this repository to change; both need a key a person holds, which is not code.

## What the exploration actually found

The installer verified attestations with `--repo` alone. That asserts only that
*some* workflow in this repository attested those bytes.

Only `release.yml` holds `attestations: write`, so nothing was exploitable. But
that is a one-line change away from being untrue, and a verification step
should not rest on a permission staying where someone left it. The installer
now pins the signing workflow:

```text
Provenance  : attestation verified against sansyourways/... (release.yml)
```

Where the GitHub CLI is too old to pin, it verifies what it can and says so
rather than printing the stronger message:

```text
Provenance  : attestation verified against sansyourways/...; this gh cannot pin
              the signing workflow (needs a newer GitHub CLI)
```

A weaker check that reads like the stronger one is worse than no check, because
it gets trusted. Tightening what the existing signature proves turned out to be
worth more than adding a second signature on top of it.

## Validation

- `./tests/regression.sh` — passed, with a new block: `reveal: 4 password
  inputs, each with a control, and the RTL wrapper follows its field`
- The installer decision table grew from 7 cases to 9: an attestation minted by
  the wrong workflow must abort, and a CLI that cannot pin must say so.
- Rendered in Chromium in both directions; the RTL collision came from looking
  at the Arabic page, not from an assertion.
