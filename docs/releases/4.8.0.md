# Sans Password Manager 4.8.0

A security key opens the vault, and the last item on the architecture board
leaves it by being run rather than by being argued about.

## The item this closes

**Hardware-backed key wrapping** has sat on the roadmap since 3.x with one
sentence against it: *needs a FIDO2 key or a TPM to test against*. That was the
whole blocker. The rule that put it there is the one 4.0.0 established — crypto
ships when there is a way to run it, not when the code reads correctly — and
for four releases there was no way to run this one.

There is now. Chromium's virtual authenticator implements the WebAuthn **PRF**
extension, which means the ceremony this feature is built on can be driven end
to end in a browser: enrol a key, sign out, and open the vault with it. The
feature is not shipping because someone finally wrote it. It is shipping
because it can now be executed.

## What it does

Set a relying-party id and the Dashboard grows a **Security Keys** page.
Enrol a key there, and the sign-in screen offers *Unlock with a security key*.
Touch the key and the vault opens. There is no master password in that path at
all — not typed, not remembered, not held anywhere.

## How the vault key gets sealed under a device

A WebAuthn credential that supports PRF will derive 32 deterministic bytes from
a salt: the same key and the same salt always give the same bytes, and no other
key gives them. SPM seals the vault key under those bytes and stores the result
beside the vault in a `.hardware` file, mode 0600.

That file is the whole feature, and what it discloses if taken is worth stating
plainly: which credential ids are enrolled, and a vault key sealed under 32
bytes that exist only inside an authenticator. Unlike the master-password
envelope sitting next to it, there is no password in that path for an offline
attacker to work on.

The keys live **beside** the vault rather than in it, and that was a correction
rather than a preference. The first design put them in a `META_` row, which is
inside the encrypted vault — readable only by someone who has already opened
it, which is exactly the person who does not need them. A cold unlock has to
read them first.

One salt per vault, not one per key. The salt has to be chosen before the
ceremony, and the ceremony is what reveals which key answered, so a per-key
salt cannot be selected at the moment it would be needed. It costs nothing: the
PRF result is per credential, so two keys given the same salt derive two
different secrets and seal two different envelopes — and the regression suite
asserts that neither opens the other's.

## No signature is checked, and that is a decision

The server verifies no assertion signature on the unlock. What proves the
caller holds the key is that the secret it supplies unwraps the vault key: if
it does not, the seal's authentication tag fails and there is nothing left for
the server to decide. Verifying a signature as well would be a second, weaker
statement about the same fact, and it would put a server-side "yes" on a path
that currently has none to subvert.

## A session with no master password

This is the part that had to be built carefully, because everything above it
assumed a session always holds one.

A session opened by a security key stores `None` where the master password
would be. Every route reaches that through one accessor, which hands back a
sentinel that is *truthy* — so every `if not master` guard written before
security keys existed keeps admitting the session unchanged, with no per-route
opt-in to forget — and is recognised by identity, never by value, so the places
that need a real password can refuse it instead of using it.

**Writes keep the key envelope.** `write_vault` gained a mode that reseals the
data under the existing vault key and leaves the key envelope exactly as it
found it. Without it, a write from one of these sessions would have resealed
the vault under the empty string, and nothing on screen would have said so. The
core refuses a password-less write that is not given the vault key, and a core
test asserts that an empty-string master is still treated as a real password.

**Two things it cannot do**, both because they use a password it never had:

| Refused | Why |
| --- | --- |
| changing the master password | there is nothing to compare the typed "current password" against, and accepting one would let anyone holding the key set the password that also opens the vault |
| restoring a snapshot | a restore installs a vault sealed under a different vault key — the key every enrolled credential wraps — invalidating the only credential the session holds, with no password on hand to recover with |

The restore is refused before the snapshot name is read, so the route is
unavailable to the session rather than conditionally available.

**And one thing that ends it.** If the vault is replaced under a live
security-key session, there is no password to re-derive a key from. The session
ends, and the reason is written to the events log — the one page still readable
while locked, and the only place a user could otherwise learn why their key
suddenly opens nothing.

## Security-key events

Enrolments, removals, refused keys and replaced vaults are recorded. The events
vocabulary is closed on purpose — free text is how a device label reaches a log
in the clear — so `hardware` joins the kinds and four values join the reasons.

The first version of this code wrote free text. `record_event` swallows what it
cannot encode, so every one of those events was silently dropped and nothing
said so. The core test now covers the vocabulary the Dashboard actually uses,
and refuses a device label offered as a reason.

## What the browser is asked for

Enrolment creates a **discoverable** credential with user verification
required. Discoverable, so the sign-in page can ask for "whatever you hold"
instead of publishing a list of credential ids to anyone who loads it — the
regression suite asserts that page carries no credential id. User verification
required, because possession of the key alone would otherwise be possession of
the vault.

The sign-in page carries two values before there is any session: whether a key
is enrolled, and the salt. Neither is a secret — deriving the wrapping key
needs the authenticator, and using it needs the vault file — and the button's
presence would disclose the first anyway.

A key nobody enrolled, a malformed secret and a secret that does not fit the
envelope are three different facts with one answer. Telling them apart would
let a caller sort its guesses; the suite compares the two response bodies byte
for byte.

## Testing

`tests/dashboard-hardware.mjs` drives a real WebAuthn ceremony against
Chromium's virtual authenticator: enrol, sign out, open the vault, sign out,
open it **again**. The second unlock is the point — one success could be luck,
and the design rests entirely on the PRF returning the same bytes for the same
salt. Then a second authenticator, enrolled with nothing, is refused.

`tests/regression.sh` drives the server half over HTTP with a stand-in secret,
because what the server has to be right about is what it does with 32 bytes,
not where they came from.

Every mutant written for this release was killed:

| Mutation | Killed by |
| --- | --- |
| the wrapping key ignores the secret | one key opened another key's envelope |
| a disagreeing salt is accepted | the salt that lost a race was enrolled |
| the security-key file is world readable | the file mode |
| a damaged file reads as "no keys enrolled" | it was not reported |
| a password-less write reseals under the empty string | the master password stopped opening the vault |
| a label reaches the file unflattened | the label was not truncated |
| the last key leaves the file behind | the file survived |
| the sentinel is used as a password | the master password stopped opening the vault |
| a replaced vault is re-derived from the sentinel | nothing was recorded |
| a refused key is not recorded | the events log was silent |
| an unenrolled credential id is named as such | two refusals answered differently |
| a stale envelope is accepted | a damaged vault opened a session |
| the sign-in page always offers the ceremony | it offered one with no key enrolled |
| the sign-in page names the enrolled credentials | credential ids on the sign-in page |
| the unlock trusts the credential id alone | the right secret was refused |
| the enrolment is not discoverable | a cold sign-in could not find the credential |
| the enrolment salt is not echoed back | the enrolled key did not open the vault |
| the master-password guard is dropped | the password could be changed |
| the snapshot-restore guard is dropped | the restore was offered |

Two of those started as survivors and are worth recording, because both were
tests that could not fail rather than code that was wrong.

The guard that ends a security-key session when its vault is replaced changed
nothing observable — the request failed either way — so the mutant lived. It
was made observable by recording the reason, which the feature wanted anyway:
the session simply ending is exactly the failure a security-key user cannot
diagnose from the screen.

The refusal for a vault file that is not a container at all was unreachable
from every test written, because a *wrong key* raises rather than returning
nothing. Reaching it needed the other case: a truncated or half-written file.
Without the guard that request does not refuse — it crashes.

A third weakness was found by the mutants rather than by review: a failed
browser step reported only "Navigation timeout of 30000 ms exceeded", which
reads the same wherever it happens. Each wait now says what it was waiting for.

## Upgrading

Nothing to do. Enrol a key from **Settings → Security Keys** if you want one;
the Dashboard behaves exactly as before if you do not. The feature and its
endpoints do not exist at all without a relying-party id, the same rule
biometric unlock has always followed.

**Treat an enrolled key the way you treat the master password.** It opens the
vault on its own. That is the entire point of it, and the entire cost.
