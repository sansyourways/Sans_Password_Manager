# Sans Password Manager 4.1.0

The roadmap's last open "Now" item was *"keep import/export fixtures
synchronized across every documented format"*. Checking that properly is what
this release is, and it found that they were not synchronized at all.

## The round trip was counting, not comparing

The suite exported the vault in each of the twenty documented formats, imported
it back, and asserted that ten records came out. Ten always came out. A format
that returned the right number of rows with a column missing passed every time.

Compared field by field instead, on a fixture carrying a comma, a doubled
quote, a tab, a newline, non-ASCII, a folder and two custom fields, the result
was the same on all twenty:

```text
csv-noheader: password/1 folder became '' (was 'Work/Ops')
csv-noheader: password/1 fields became () (was (('Account number', ...)))
```

**The CLI lost every folder and every custom field, on every format.** The
export never wrote those columns and the import never read them — while the
Dashboard did both. Two surfaces, two answers, which is the disagreement a
shared trusted core exists to make impossible.

If you have an export taken with 4.0.1 or earlier, it does not contain those
columns. Re-export it.

## `spm export sql` produced SQL nothing could load

```text
$ sqlite3 :memory: < spm_export.sql
Parse error near line 2: 9 values for 8 columns
Parse error near line 3: 9 values for 8 columns
```

Every row, since `url` was added. The `CREATE TABLE` and the `INSERT INTO`
named eight columns while each row wrote nine; the Dashboard's version wrote
eleven against the same eight. SPM's own importer parses the VALUES tuple
positionally and ignores the column list entirely, so the round trip passed:
SPM was reading back exactly what SPM wrote, and only SPM could.

The suite now loads the SQL export with `sqlite3` — a real parser, and not the
one that wrote the file.

## One column order

Five places each kept their own copy of the export's columns, and each stopped
somewhere different: the CLI SQL writer at `extra`, its reader at `url`, both
headerless CSV readers at `url`, the web SQL writer at `extra`. None of them
failed a test, because every reader was fed by the writer that matched it.

`EXPORT_FIELDNAMES` in the trusted core is now the one ordered definition.
Writers join it, positional readers map against it, and the SQL readers take
their names from the statement rather than from any list at all. The exported
CSV header is asserted to equal it, so a column added to an exporter without
being added to the order fails there rather than in whichever reader silently
maps it onto the wrong name.

## A file that was never encrypted could pass for a vault

Bundle restore, history restore and sync pull all prove a file opens before
replacing the live vault. That proof was "the decrypt command exited zero",
and gpg exits zero on inputs it never decrypted: an unencrypted OpenPGP
literal-data packet is parsed and emitted as-is.

Measured, because the rate matters:

```text
gpg exited 0 on 34 of 3000 random 512-byte blobs (1.13%)
```

Byte 0 is read as a packet header, and a few tags are processed without a key.
So a file that is not a vault at all could satisfy the guard and replace one.
All three callers now require the decrypted bytes to look like a vault — any
`META_` row or any record line, deliberately generous, because this exists to
reject files that are not vaults rather than to start refusing odd ones.

### The same measurement closed an old flake

The sync suite published **512 random bytes** as its "undecryptable" remote and
asserted the pull refused them. At 1.1%, across three transports, that is a ~3%
chance per run of `an undecryptable remote was installed` on a file that had
been parsed rather than opened. It was observed twice in CI, on two different
transports, and never reproduced locally — because it was a coin flip, not a
race.

The fixture is now a fixed string, and it asserts its own undecryptability
before relying on it: if it ever stops being undecryptable, that is what fails,
rather than the assertion it exists to support.

## Validation

- `python3 tests/core-test.py` — **105 tests** (was 104)
- `./tests/regression.sh` — passed, with a new block:
  `formats: 20 round-tripped field for field, and the sql export loads in sqlite`
- Mutation-tested. Restoring the headerless CSV reader to its old hardcoded
  list is killed with the exact original symptom, named down to the field:
  `csv-noheader: password/1 folder became '' (was 'Work/Ops')`. Ignoring
  `--require-vault`, or making `looks_like_vault` accept anything, each fail
  their own core test.

## Upgrading

No format change to the vault and nothing to run. The **export** format gains
two columns, `folder` and `fields`, at the end of every row; readers that take
columns by name are unaffected, and SPM reads exports from earlier releases
unchanged.
