# Sans Password Manager 4.0.0

The vault stops being sealed by gpg. It is now encrypted with AES-256-CTR,
authenticated with HMAC-SHA256, and unlocked through scrypt — and it is roughly
four times faster to open as a result. The idle lock in web mode also stops
being fixed at thirty seconds.

This is a major version for one reason: **a vault this release writes cannot be
opened by 3.15.0 or earlier.** Nothing else in it breaks.

## Why gpg had to go

Format 3 separated the vault key from the master password: the vault is sealed
under a random 256-bit key, and only that key is sealed under the password.
That is what makes a password change cost a few hundred bytes instead of a
re-encryption, and what lets a recovery file survive one.

Then it stretched both of them. gpg's job is to turn a guessable passphrase
into a key, so it iterates SHA512 sixty-five million times — correct for the
master password, and pure waste for a value that is already 256 random bits.
Half the cost of every vault read was spent hardening something that had
nothing left to harden.

So the stretching now happens once, where the guessable secret actually is:

| | gpg | 4.0.0 |
|---|---|---|
| master password | SHA512 × 65,011,712 | scrypt, n=32768, r=8, p=1 (32 MiB) |
| vault key → data | SHA512 × 65,011,712 | none; the key is already uniform |
| cipher | AES-256 (CFB) | AES-256-CTR |
| authentication | none | HMAC-SHA256, encrypt-then-MAC |

Measured on a 200-record vault:

```text
cold read (unwrap + decrypt)    663 ms  ->  168 ms
warm read (vault key held)      248 ms  ->   11 ms
```

scrypt is memory-hard where SHA512 iteration is not, so the slower half is also
the stronger half. Argon2id is still not reachable on the platforms SPM
supports — OpenSSL 3.2 or a third-party dependency, and this project takes
neither — but the vault now **records its KDF by name and parameters**, which
turns adopting it later into a value the reader dispatches on rather than
another format change.

## The vault is authenticated now

This is the part that is not about speed. gpg's symmetric mode gave the vault
no integrity, so a modified vault and a wrong master password produced the same
refusal, and SPM's own event log had to say so — `reason=bad-master` was the
honest answer because nothing could tell the difference.

Every sealed block now carries an HMAC-SHA256 tag over its magic, its salt, its
IV and its ciphertext, checked *before* anything is decrypted. The two failures
have opposite remedies, and they finally read differently:

```text
$ spm get 12
that secret does not open this vault

$ spm get 12
this vault's data failed authentication; the master password was right, so the
file itself is damaged -- restore the .bak or a history snapshot beside it
```

## Upgrading: nothing to run

Your vault upgrades in place the next time anything writes it — adding an
entry, editing one, changing the master password. Reading a gpg vault keeps
working indefinitely, so there is no flag day and no migration command.

**The vault key does not change.** That is what makes the upgrade invisible to
everything downstream: the recovery file still names the same key, a Shamir
share set minted in 3.14.0 still reconstructs it, and a `.bak` from before the
upgrade still opens under the same master password.

`spm doctor` reports which backend is actually on disk, rather than which one
this build would write:

```text
vault_cipher  ok    sealed with AES-256-CTR and HMAC-SHA256; key derivation
                    scrypt n=32768 r=8 p=1
```

**Do not downgrade after upgrading.** 3.15.0 cannot read the new container at
all and will report a wrong master password, because from its point of view
that is indistinguishable from what it sees. Keep the release archive you
upgraded from if you want a way back; the `.bak` beside the vault is still in
the old format until the second write.

## Three constraints the implementation did not get to choose

openssl is the cipher because it is the only one on every platform SPM
supports: Python's `hashlib` carries scrypt, HMAC and PBKDF2 but no AES, and a
third-party dependency is the portability rule this project is built on. Using
its command line imposed three things, and each shaped the code rather than
being worked around.

**Keys reach it on a file descriptor.** `openssl enc -K` puts the key in argv,
where any local user reads it out of `/proc/<pid>/cmdline`. OpenSSL 3 scrubs
argv shortly after startup, but there is a window, and LibreSSL is not known to
scrub at all.

**A passphrase read from that descriptor is read as a line.** A raw 32-byte key
containing a `0x0A` byte would be silently truncated — and the vault would
encrypt and decrypt perfectly afterwards, under a key a fraction of the
intended length, with nothing anywhere reporting a problem. Everything passed
to openssl is base64, and key material containing a newline is refused rather
than trusted.

**Authentication is ours.** `openssl enc` has no AEAD mode that carries a tag,
so the construction is explicit encrypt-then-MAC with a MAC key derived
in-process that never crosses to another program.

## What the tests had to prove

A round trip proves nothing here: a build whose openssl derived a different key
would encrypt and decrypt perfectly against itself and produce vaults no other
machine could open. So the suite carries known answers — a fixed key, salt, IV
and plaintext against fixed ciphertext, and a check that openssl's
`-pbkdf2 -iter 1` is byte-for-byte `hashlib.pbkdf2_hmac`, which means the
derivation the format states is the one the command line performs.

The MAC coverage is tested by mutation rather than by assertion. Authenticating
only the ciphertext still round-trips, still rejects a wrong key, and still
passes every obvious test — and quietly lets an attacker move the IV and change
what CTR produces. That mutant is killed by a bit flipped at offset 14.

## Configurable idle lock

The dashboard auto-lock was thirty seconds and only thirty seconds, which is
right for a phone left on a table and wrong for anyone reading a long note or
copying a card number off the screen. Settings now offers 15s, 30s, 1m, 2m, 5m,
10m and 15m, per vault. Thirty seconds stays the default.

It is a short list rather than a text box on purpose: a number typed into a
field invites 86400, and a list is a policy someone chose from. A value edited
into the config file by hand is treated as absent rather than obeyed, because
this setting decides how long a decrypted vault sits on an unattended screen
and an unreadable one must fail towards the short end.

The server-side idle bound follows it upward. That bound is the control that
still holds when the browser's JavaScript does not run — which is not
hypothetical; a CDN rewriting inline scripts disabled the browser lock outright
once. If it stayed at five minutes, a fifteen-minute lock would be a promise
the server breaks. At the default it is unchanged, at 300 seconds.

## Also in this release

- The dashboard login caught only the refusal gpg produces. Once a vault was on
  the new format, a wrong master password reached the user as a server error
  and skipped the failure counter that rate-limits guessing.
- `parse_container` accepted an AEAD header, because that header also carries a
  KEY line and a DATA marker, and returned an envelope no gpg could open.
- The overview console printed "GnuPG boundary active on this host"
  unconditionally. It now reads the cipher off the vault file and the lock
  timer off the setting, so neither line can go on being true-shaped and wrong.
