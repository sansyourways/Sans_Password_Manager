# Sans Password Manager 3.4.3

Bitwarden imports, and the discovery that the existing ones were worse than
broken.

## What was already wrong

A Bitwarden CSV, imported through web mode, produced **one empty note**. Every
login was silently dropped, and the dashboard reported "Vault successfully
updated". A Bitwarden JSON export raised `AttributeError` and imported nothing
at all.

Bitwarden's export shares no field names with SPM's, so the importer read
`name`, `login_username` and `login_password` as absent and mapped the rows to
nothing. Nothing about that failure was visible to the person doing it.

## What works now

All three Bitwarden export files, each with its own entry in the import format
list:

| Bitwarden export | Choose |
|---|---|
| `.json` unencrypted | **Bitwarden — JSON export** |
| `.csv` | **Bitwarden — CSV export** |
| `.json` password-protected | **Bitwarden — password-protected JSON** |

Picking plain `json` or `csv` for a Bitwarden file works too — the shape is
detected. That is deliberate: the previous behaviour for a wrong pick was
silent data loss, so guessing correctly should not be the user's job.

**Logins** become password entries with their username, URI and notes.
**TOTP** becomes an authenticator, and an `otpauth://` URI is unpacked into its
secret, period and algorithm — SPM's authenticator row holds a bare secret, and
a URI stored there would be base32-decoded and generate nothing.
**Secure notes** become notes. **Cards and identities** have no SPM equivalent
and are kept as readable notes rather than dropped, because an import that
quietly loses a card is the failure people discover months later. **Folder
names** and **custom fields** are appended to each entry's notes.

The mapping lives in the trusted core, so the CLI and the dashboard cannot come
to different conclusions about what a Bitwarden file contains.

## Password-protected exports

The password you set when exporting is asked for in the form, used to read the
file, and never stored.

Bitwarden protects an export with PBKDF2-SHA256 over the export password, an
HKDF split into an encryption key and a MAC key, and AES-256-CBC with an
HMAC-SHA256 tag. SPM verifies the tag **before** decrypting, in constant time,
which is why a wrong password is reported as a wrong password rather than as a
corrupt file.

Two limits, both reported rather than guessed at:

**Argon2id exports cannot be read.** There is no Argon2 implementation SPM can
reach without a third-party dependency — the same wall documented in
`ROADMAP.md` for SPM's own vaults. Such a file is refused by name, with the
advice to re-export without a password or as CSV.

**AES-256-CBC needs the `cryptography` package.** Where it is absent the import
says so. The alternatives were both worse: `openssl enc -K` puts the key in
argv, where any local user can read it, and the trusted core forbids that by
design; and hand-writing AES does not belong in a password manager for the sake
of a one-off conversion. Unencrypted JSON and CSV need nothing beyond the
standard library, and are the paths most people will use.

## Upgrade and compatibility

No vault-format migration. Existing import formats are unchanged, and the
regression suite still covers all twenty of them.

## Verification

- Generated `spm.sh` reproduced from `src/`
- Full disposable-vault regression suite passes
- The encrypted fixture is built independently, the way Bitwarden builds one,
  so the decryptor is tested against a file it did not produce
- Four refusals asserted: no password, wrong password, tampered ciphertext,
  and an Argon2id export
- Three mutations caught: removing the Bitwarden dispatch, storing the
  `otpauth://` URI instead of its secret, and skipping the HMAC check — the
  last one caught because a wrong password then produces an unhelpful padding
  error instead of saying the password is wrong
