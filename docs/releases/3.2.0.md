# Sans Password Manager 3.2.0

3.1.0 shipped the universal browser extension but left its installation as a
loop: build the package, load it unpacked, read the 32-character ID the browser
generated, paste that ID back into a second command, restart the browser. The
ID was derived from the install directory, so it differed on every machine and
could not be documented. 3.2.0 removes that loop.

## One command

```bash
./browser-extension-universal/setup.sh
```

This detects an installed browser, builds the matching Chromium or Firefox
package, registers the native host, opens the browser's extensions page and the
prepared folder, and prints the clicks that remain. Nothing is copied back into
the terminal.

`--browser NAME` selects explicitly among chrome, chromium, edge, brave,
vivaldi, opera, and firefox. `--no-open` prepares everything without opening
windows, for a remote machine or a scripted install. Linux and macOS are
supported.

The manual `build.sh` and `install-host.sh` steps remain documented in
`browser-extension-universal/README.md` for troubleshooting.

## A stable, derived extension identity

The Chromium manifest now carries a public development key, so every unpacked
copy loads under the same ID: `infdncbkefpjncplegccokcfpiicadlo`.

This is a development identity, not a secret and not a signing credential. It
exists only so the native-host registration can name the extension in advance.
Browser store signing remains a separate matter.

`extension-id.sh` derives that ID from the manifest key the same way the
browser does — the first 16 bytes of the key's SHA-256, hex-mapped onto a-p.
`setup.sh` and `install-host.sh` both call it rather than each carrying a
literal, so a key rotation cannot leave one of them registering a host for an
ID no browser will assign. CI asserts the derived value against the ID quoted
in the documentation and in the regression suite.

## Upgrading

**Remove any previously loaded unpacked SPM extension before loading the new
one.** Earlier builds had no key, so the browser derived the ID from the
install directory. Adding the key changes that ID, and the browser treats the
rebuilt extension as a separate one: the old entry stays installed, and its
native-host registration no longer matches. Re-running `install-host.sh` also
rewrites any Chromium manifest that had been registered against a previous ID.

There is no vault-format migration. Vaults, recovery material, CLI commands,
and the Dashboard are unchanged from 3.1.0.

## Also in this release

The CI whitespace gate had never run. It diffed the repository's root commit
against `HEAD`, but the checkout was shallow, so the root resolved to `HEAD`
and the check compared a commit to itself and passed unconditionally. It now
fetches full history and checks the lines a change actually adds.

The macOS half of the extension-registration test asserted Linux native-host
paths, which would have failed the macOS CI job. It now selects paths per
platform.
