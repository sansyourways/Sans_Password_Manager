# Sans Password Manager 4.0.1

Fault tolerance for the two paths the roadmap still listed as uncovered.
3.4.0 covered the write path and the lock — disk-full, killed mid-write,
corrupted vault, competing writers — and left restore and import for later.
This is later.

## `spm restore` was the one write that could not be undone

Every other path that changes a vault archives the previous generation and
leaves a `.bak` beside it. Restore did neither. It copied whatever the bundle
held over the live vault and, until 4.0.1, never checked that the bundle
opened:

```text
$ spm restore                 # bundle vault truncated by a bad USB copy
Vault already exists at /home/you/.spm_vault.gpg. Overwrite? (yes/NO): yes
Vault moved to /home/you/.spm_vault.gpg.
```

A working vault destroyed, replaced by one that opens nothing, and reported as
success. Now:

```text
$ spm restore
Vault already exists at /home/you/.spm_vault.gpg. Overwrite? (yes/NO): yes
Master password:
Error: The bundle vault did not open with that master password, so the vault
already at /home/you/.spm_vault.gpg was left untouched.
```

**The password prompt is new, and only when there is something to lose.**
Restoring onto a machine with no vault asks for nothing — the check exists to
protect what is already there, and demanding a password on an empty machine
would break staging a bundle for someone else to open later.

Two more things restore got wrong, both of the same shape — the code knew about
a vault, but not the one it was acting on:

- It held the **bundle's** advisory lock while overwriting `~/.spm_vault.gpg`.
  During a restore `VAULT_FILE` is the bundle, so the lock the CLI takes
  protects the file being read and not the file being replaced. A dashboard
  write to the real vault could interleave with the rename that overwrote it.
  Restore now takes a second lock, on the destination.
- It deleted the vault from the bundle **before** installing the recovery file,
  so any failure after that point left a bundle holding a recovery file and no
  vault. The bundle is consumed only once both files have landed.

## One install path instead of three

`restore`, `history-restore` and `sync pull` each carried their own
`cp` / `chmod 600` / `mv -f`. Only two archived anything, only one verified a
digest, and **none of them fsynced** — so a crash immediately after any of them
could leave the new name over blocks that were never written.

All three now call `install-file` in the trusted core, which does the whole
sequence once:

```text
stage beside the destination  ->  chmod 600  ->  verify the digest, if one was
given  ->  archive the previous generation and copy it to .bak  ->  fsync the
staged file  ->  atomic rename  ->  fsync the directory
```

The ordering matches `write_vault`, and for the same reason: the archive and
the `.bak` are taken **before** the rename, because after it there is nothing
left to copy. A refusal at the digest check leaves the destination untouched
and no `.bak` of a vault it never replaced.

Recovery files skip the archive — a recovery file has no history directory of
its own, and archiving one would file it under a scope derived from its own
path — but they still get a `.bak`, because that file is the only wrapper
around the previous vault key.

## A reviewed import now survives a failed write

The web import holds the reviewed rows in the session and hands back a one-use
token. Confirming took that token and **cleared the review before writing the
vault**. The reasoning behind clearing was sound for two cases: a token that
failed to match must not get a second attempt, and a successful import must not
be replayable.

It also threw the review away when the *write* failed — a full disk, a locked
vault — costing the user the entire upload and review for a failure that had
nothing to do with the token.

Consumption moved to after the write returns. The two cases the clearing exists
for still clear; the third one no longer does. A guess at the token still gets
exactly one attempt, an expired review is still gone, and a completed import is
still not replayable.

## Validation

- `python3 tests/core-test.py` — **104 tests** (was 100), four of them new
  fault injections against the install path: a full disk while staging, a
  digest that does not match, replacing versus creating, and skipping the
  archive without skipping the backup.
- `./tests/regression.sh` — passed, with two new blocks:
  - `restore: a bundle that will not open is refused; the replaced vault
    survives as .bak and a snapshot`
  - `import: a review survives a failed write, and still refuses replay,
    guessing and expiry`
- Mutation-tested. Removing the bundle verification is killed by *"restore
  installed a bundle that does not open"*; clearing the review before the write
  again is killed by *"a failed write threw the review away"*; dropping the
  `.bak`, the archive, or the digest check each fails its own core test.

## Upgrading

Nothing to do, and no format change. A vault written by 4.0.0 is read and
written identically by 4.0.1.
