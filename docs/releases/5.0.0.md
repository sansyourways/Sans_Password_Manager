# Sans Password Manager 5.0.0

Typed records: one schema engine, and the first key types built on it. A
password manager keeps more shapes than a password — an API token has an
environment and an expiry, a database credential has a host and a port, an SSH
key opens a machine — and until now the extra parts went in the notes field,
where nothing could search, redact or check them. This release gives those
shapes a home, in the CLI and the Dashboard from the same schema.

The major version is for the new record kinds and the engine under them, not
for a format break. A 4.x vault opens unchanged, and a vault carrying typed
records is still a tab-separated file that `grep` reads.

## What changed

Seven record types now store what their shape actually has: `api-token`,
`db-credential`, `credit-card`, `identity`, `software-license`, `wifi` and
`server`. One schema in the trusted core — `RECORD_SCHEMAS` — names each type's
fields, which of them are secret, which are required, and its icon. The CLI
prompts, the Dashboard form, the record list, the redaction, and all twenty
export formats read that one definition. Neither surface keeps its own list of
fields, which is what stops them from disagreeing about a record.

```bash
spm record types
spm record add wifi
spm record list
spm record view wifi 1            # secrets masked
spm record view wifi 1 --reveal
```

Ids are allocated per type, so `wifi 1` and `server 1` both exist and each
type counts from one. Every command that takes an id takes the type with it —
an id on its own is half an address.

In the Dashboard, a **Records** section lists every typed record with per-type
filter chips, **+ Add Record** draws the form for the chosen type, and a
record's page masks each secret behind the same reveal-and-copy control the
password pages use. Records are counted on the overview and found by search —
by label, id, folder, any non-secret field, or a custom field's name. Secret
fields are never searched, so a result count cannot answer "is this string in
the vault?" for anyone reaching an unlocked session.

## Three key types, everything public derived from the key

The first three types built on the engine are keys, and they share one idea:
what is public about a key is not typed or stored, it is computed from the
stored key every time it is shown.

**SSH keys (`ssh-key`).** Stores the private key, its passphrase and the hosts
it opens. Derives the fingerprint, key type, size and public key by parsing the
`openssh-key-v1` container in pure Python — without the passphrase, without a
temporary file, and without shelling out to `ssh-keygen`, because the container
keeps the public half in the clear.

```bash
spm ssh import ~/.ssh/id_ed25519 "work laptop"
spm ssh list
spm ssh show 1
spm ssh public 1
```

**The SSH agent.** A key in the vault still has to reach `ssh`, so `ssh load`
hands it to `ssh-agent` over a pipe — `ssh-add -t <seconds> -` reads it on
stdin, never a file and never a command-line argument. The default lifetime is
15 minutes, which is the Dashboard's longest idle lock rather than an invented
number; a sealed key's passphrase reaches `ssh-add` over an inherited file
descriptor; and unloading names the key by its public half alone, so it never
touches the private one. SPM will not start an agent you did not start
yourself.

```bash
spm ssh load 1            # 15 minutes
spm ssh load 1 60         # an hour
spm ssh unload 1
spm ssh agent             # what the agent holds, and what came from this vault
```

This one is CLI-only on purpose. An `ssh-agent` belongs to a session on a
machine, not to a vault, and the Dashboard can be published on a domain and
reached from elsewhere — where "load into the agent" would load into the
host's agent, not the clicker's.

**GPG / OpenPGP keys (`gpg-key`).** Stores the armored secret key and its
passphrase. Derives the fingerprint, key id, algorithm, curve or size, creation
date, identities and subkey count — matching `gpg`'s own fingerprint without
gpg, without a keyring or agent, and without the passphrase, because an
OpenPGP secret key carries its public half in the clear just as an SSH key
does.

```bash
spm gpg import ~/backup/signing.asc "signing key"
spm gpg list
spm gpg show 1
```

## Why derived, and not typed

A stored fingerprint is a claim, and claims drift. Edit the key and a stored
fingerprint keeps describing the key that used to be there — which is exactly
backwards, because the fingerprint is the thing you check to know *which* key
this is. A derived fingerprint cannot be wrong about its own key: if it renders
at all, it is the fingerprint of the bytes in the record.

The Dashboard shows a **Derived from the key** panel below the fields,
recomputed on every draw. Nothing in the record page knows what an SSH or GPG
key is: a schema names a deriver, the page asks the core for that record's
derived rows and its heading, and renders what comes back. GPG landed with no
new Dashboard code beyond an icon and its translations.

## Ways to be wrong that this is not

- **A truncated key gets no plausible fingerprint.** Slicing past the end of a
  byte string does not raise in Python — it returns something shorter, which
  hashes to a fingerprint that is wrong and looks right. Every length field in
  both parsers is bounds-checked, so a cut-off key derives nothing and says
  why.
- **A key's size is measured honestly.** RSA in bits of the modulus, not bytes
  — a 2048-bit key stored with a leading zero byte is not 2056-bit. An
  elliptic-curve key by its curve, not the bit length of an encoded point — an
  Ed25519 point measures 263 bits and is not a 263-bit key.
- **A public key is refused at import.** It fingerprints exactly like a secret
  one, so a guard that only asked "did this fingerprint?" would file it as the
  secret half of a key that could then neither sign, decrypt, nor open a host.
- **A key SPM cannot read is still kept.** An unrecognised format or an old PEM
  key derives nothing and gives the reason, rather than being dropped.

## What did not change

The vault format. A vault written by 4.x opens unchanged, and a vault holding
typed records is still the same tab-separated plaintext under encryption: one
row per record, the type in the row tag, the secret-bearing payload base64 in
one field. Counting records, listing one type, or describing a damaged row
never decodes anything, and the file stays greppable by anyone holding only the
plaintext and `grep`.

Secret key material never travels on a command line. `core record row`, `core
ssh info` and `core gpg info` take their values as base64 on stdin, because
argv is world-readable on Linux.

## Testing

- 158 core tests, including known-answer vectors for SSH and OpenPGP
  fingerprints pinned as **public** keys, with the secret-key packets the tests
  need built byte by byte — so no private key material lives in the repository.
- Regression coverage that drives every record type through add, list, masked
  view, delete and all twenty export formats on both the CLI and the Dashboard;
  compares SPM's SSH derivation against `ssh-keygen` and its OpenPGP derivation
  against `gpg` for three key types each, sealed keys included; drives a real
  `ssh-agent` end to end; and asserts no private key reaches a screen.
- Mutation runs over the new guards — the fingerprint hash, the truncation
  checks, the ECC size, the public-key refusals, the agent lifetime and
  stdin delivery — each proven to fail a test.

## Upgrading

Nothing to do. Your vault opens exactly as before. `spm record types` lists the
new kinds; `spm ssh import`, `spm gpg import` and `spm record add` start using
them.
