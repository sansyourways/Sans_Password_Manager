# Sans Password Manager 4.10.0

A Secret Key, so that a stolen copy of the vault file has nothing left in it to
guess at — and the scrypt cost raised, now that the header has proved a cost
parameter can move without stranding anything.

## What changed

Your vault legitimately leaves this machine. `sync` pushes it to a directory, an
rsync host or an rclone remote. `save` and `portable` write it into a bundle.
Every write leaves a `.bak` beside it and a snapshot in your history. If you run
the Dashboard on a domain, the file sits on a machine reachable from the
internet.

Any one of those copies, in the wrong hands, can be attacked offline for as long
as the attacker likes — and until now the only thing in the way was how good
your master password is.

A **Secret Key** is 128 random bits, generated once, kept off the vault file, and
mixed into the key derivation alongside your master password. With one, there is
nothing left in the file to guess at: a weak password and a strong one become
equally unbreakable to whoever holds only the copy.

It is off by default and enabled per vault.

```bash
spm secret-key            # bound or not, and where the key is
spm secret-key enable     # generate one and rewrap the vault under it
spm secret-key show       # print it again, after a master-password check
spm secret-key import     # store it on a second machine
spm secret-key rotate     # replace it; the old one stops working
spm secret-key forget     # drop this machine's copy, vault stays bound
spm secret-key disable    # back to the master password alone
```

Enabling rewraps the key envelope and nothing else, so it costs what a password
change costs rather than re-encrypting your vault.

## What it does not do

Stated here rather than left implied, because a protection people misjudge is
worse than one they do not have.

- **It is no defence against a compromise of this machine.** Anything that can
  read your vault can read the Secret Key in the data directory beside it —
  malware, a stolen unlocked laptop, an attacker who reaches code execution
  through the Dashboard. It protects copies in transit and at rest elsewhere,
  not the machine they came from.
- **An enrolled security key is a second door the Secret Key does not lock.**
  Hardware wrapping seals the vault key directly, so a security-key unlock never
  touches the password path. That is correct — a token is already a possession
  factor — but a vault with a `.hardware` sidecar is not "useless without the
  Secret Key".
- **A new device needs the key.** Carrying the vault and knowing the password is
  no longer enough. That is the trade, and it is why `enable` prints the key and
  tells you to write it down.

## Losing it is not a lockout

Recovery does not go through the master password at all. The recovery file seals
the **vault key**, and split recovery reconstructs the **vault key**; neither
derives anything from what you type. A recovery file, or a threshold of Shamir
shares, still opens a vault bound to a Secret Key you no longer have, and lets
you rewrap it under a new password and a fresh key.

## Where the key is kept

Not beside the vault. `.recovery` and `.hardware` sit next to the vault file
because they are useless to a thief on their own; a Secret Key is the opposite,
and its whole value is that it does not travel with the copies.

```text
~/.local/share/spm/secret-keys/<scope id>     mode 0600
```

Nothing that copies a vault reaches in there: the sync transports move one file,
and the bundle exporter writes the vault, not your data directory. `doctor`
audits the file's permissions along with everything else sensitive.

`SPM_SECRET_KEY` supplies it from the environment instead, for headless runs and
for a machine that has the vault but not yet the key.

## How the vault records it

One field on the header line that already carries the derivation parameters:

```text
KDF scrypt n=65536 r=8 p=1 salt=<base64> sk=1
```

Absent means no, which is what every vault written before this release says by
saying nothing — so old vaults keep opening and the format version does not
move. The field is unauthenticated, like the cost parameters, and fails closed
the same way: strip `sk=1` and the reader derives a different key, the
envelope's tag rejects it, and you are told the secret does not open this vault.
There is no downgrade to a weaker vault that still opens.

## A missing Secret Key is not a wrong password

A vault bound to a key this machine does not hold is a named state. The core
exits with its own status for it, and the CLI, the Dashboard and `doctor` each
say what is actually missing. The Dashboard also declines to count it against
the five-attempt sign-in lockout — retyping a password that was already correct
cannot help.

## scrypt at n=65536

64 MiB and about 305 ms, against 32 MiB and about 124 ms before. An offline
guesser drops from roughly eight attempts per second per core to three.

Nothing is stranded. The `KDF` line has recorded the derivation by name and
parameter since 4.0.0, and the reader uses the vault's own numbers rather than
the running build's — which is exactly what makes this change safe. A vault
written at `n=32768` keeps opening, and its next write carries it up, with no
format change and no new vault key.

`n=131072` was measured too (128 MiB, ~547 ms) and not taken: scrypt's cost is
memory, and SPM runs on phones under Termux, where a vault that will not open on
the device it lives on is worse than a slower guesser.

## The seal salt stays at eight bytes

This release was planned to widen it to sixteen. It does not, and the reason is
measured rather than argued.

`openssl enc -S` answers `hex string is too long, ignoring excess`, and a
sixteen-byte salt produces ciphertext byte-identical to its own first eight. The
widening would have reached the MAC key derivation and nothing else, while the
format header claimed otherwise — a change that only looks stronger, which is
the worst kind to ship in a password manager.

Deriving the cipher key in Python would use the full width, but openssl's CLI
takes a raw key only as `-K` on the command line, and a command line is
world-readable. The measurement now sits beside the constant so the next person
checks rather than assumes.

## Testing

- A Secret Key regression block: the binding survives ordinary writes and
  password changes; a stripped `sk=1` fails closed; a missing key exits with its
  own status and is never reported as a wrong password, in the core, the CLI and
  the Dashboard; an empty key file is damage rather than absence; a key from
  another vault is refused on import; rotation retires the old key; and a sync
  push carries the vault and nothing else.
- A scrypt-cost block that writes a vault at the old `n`, proves it still opens,
  and proves its next write raises it while keeping the same vault key.
- **Seventeen mutants of the new guards, all killed.**

The scrypt known-answer test was restructured rather than given a new vector. It
called `derive_kek` with defaults, so it tracked `KDF_N` — and regenerating its
expected value would have derived it from the very constant the test exists to
check. It now pins `n=32768` for the cross-platform vector that must never move,
and asserts the shipped cost separately, so raising it again is a deliberate
edit.

## Upgrading

Nothing to do. Your vault keeps opening exactly as it did, and the next time you
write to it the key derivation moves up on its own.

To bind a vault to a Secret Key, run `spm secret-key enable` and write down what
it prints. To go back, `spm secret-key disable`.

Security reports now go to **sans@silentprotocol.top**.
