# SPM 4.10.1

A custom field could hold a character that made your own export refuse to
import. One escaping fix. Nothing else changed, and the vault format did not
move -- 4.10.1 reads and writes exactly the vaults 4.10.0 does.

## What was wrong

`json.dumps` escapes every C0 control -- newline, tab, the record and group
separators -- but leaves U+0085, U+2028 and U+2029 as literal characters,
because all three are legal inside a JSON string. They are also three of the
eleven characters `str.splitlines()` treats as line breaks, and the ndjson,
jsonl, yaml and fallback-toml readers all split a file into lines before they
parse it.

So a custom field holding one of them exported as valid JSON and came back as
two invalid halves:

```
$ spm import ndjson backup.ndjson
json.decoder.JSONDecodeError: Unterminated string starting at: line 1 column 231
Error: Import failed.
```

## Why it was not noticed

Everything a person would check agreed the file was fine. Bash reads the
export as one line. `wc -l` counts one line. `json.loads` parses it without
complaint. Only `str.splitlines()` disagrees, and only the importer calls it.

An export that passes every check you would think to run, and fails on the day
you need it back, is the worst shape a backup bug can take.

## What changed

The three characters are now written as `\u0085`, `\u2028` and `\u2029`
escapes. JSON defines those as the same string, so `json.loads` returns
exactly what went in -- the fix is escaping, not sanitising, and no value is
altered.

The change lives in the trusted core, so the CLI and the SPM Dashboard take it
from one definition rather than two.

## If you are affected

Your vault was never at risk. A vault row stores these values base64-encoded,
so nothing was lost on the way in -- only the way out. An export written by
4.10.0 or earlier that will not import is fixed by re-exporting from the vault
on 4.10.1.

These characters reach a password manager by ordinary means: pasting a
recovery note out of a PDF or a word processor is enough.

## Verified

- 118 core tests, including one that derives the set of line terminators from
  `str.splitlines()` itself rather than from a list someone typed
- three mutants of the escaping, all killed
- the full regression suite, plus a new end-to-end test that exports a custom
  field holding each of the three characters through ndjson, jsonl, yaml,
  toml, json, csv and tsv and compares the value field by field after
  importing it back
