# Sans Password Manager 4.4.0

**Nothing about the product changed.** This release adds a way to verify part
of it that could not be verified before, and moves a roadmap item that had been
waiting on exactly that.

## The blocker

Two items on the roadmap are marked as waiting, and the reason given for both
is verification rather than code:

> - **The in-field picker** needs a browser's extension UI driven for real.
> - **Hardware-backed key wrapping** needs a FIDO2 key or a TPM to test against.

The browser-extension plan said the same thing more specifically:

> Driving an extension under headless Chromium with `--load-extension` is
> possible and worth revisiting, but it is its own project and should not gate
> 3.1.0.

It is possible. This is the first half of that project.

## What the harness does

`tests/extension-ui.mjs` builds the Chromium extension, loads it into a
throwaway profile, and asserts four things a browser can answer and a source
reading cannot:

- **The service worker starts.** That is the difference between an extension
  that is running and a directory that is merely sitting on disk. A manifest
  Chromium refuses still looks perfectly fine to `cat`.
- **The id the browser assigns is the one `extension-id.sh` derives.** 3.2.0
  gave every unpacked copy one stable identity from the manifest key, so the
  native-messaging host could name it in a file written once. Until now that
  was checked by re-deriving the id the same way the script does — which proves
  the script agrees with itself. This asks the browser. Flipping a single bit
  in the key is caught:

  ```text
  the browser loaded hcfefmknaeailbblclmjidkcjflfklgm,
  extension-id.sh says infdncbkefpjncplegccokcfpiicadlo
  ```

- **A non-web page is refused.** This is a real fill-path rule: it is what keeps
  autofill off the extension's own pages, PDF viewers and devtools tabs. A fill
  path that ran there would run anywhere.
- **Nothing secret reaches the popup DOM.** The bridge protocol is secret-free
  by construction and the suite already asserts that at the CLI. This asserts it
  where a person would actually see it.

## What it does not reach

The native-messaging round trip and the fill itself.

The popup reads the active tab to decide which host it is filling for, and an
extension page cannot honestly impersonate one — `tabs.query({active: true})`
from a page served at `chrome-extension://…` returns that page. Driving the
real fill needs tab plumbing, and faking it would produce a test that passes
while proving nothing.

That is the second half of this project, and it is what the in-field dropdown
will be built against. It is written down in both roadmaps rather than left for
someone to discover.

## Skipping is not passing

CI runners have neither Chromium nor puppeteer, so the block skips there — and
says which of the three it is missing:

```text
  extension: skipped, no puppeteer-core (set SPM_PUPPETEER_PATH)
```

Point `SPM_PUPPETEER_ROOT` at a checkout with `puppeteer-core` installed, or
`SPM_PUPPETEER_PATH` at the module itself, and it runs.

## Validation

- `./tests/regression.sh` — passed, both ways: with the harness running
  (`extension: runs in Chromium, id matches extension-id.sh, refuses a non-web
  page, and leaks nothing into the popup`) and with it skipped.
- Mutation-tested. Two mutants, and the first attempt at one was itself a
  no-op worth recording: replacing the first 32 characters of the manifest key
  changed nothing, because those bytes are the standard DER prefix every RSA
  key shares. Flipping a bit in the modulus is what actually moves the id.
