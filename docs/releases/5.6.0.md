# Sans Password Manager 5.6.0

Look-alike warnings, scoped secret access and injection, shell completion, and a
capability-sandboxed plugin SDK. No format change: 5.6.0 reads and writes exactly
the vaults 5.5.0 does.

## What's new

### Domain look-alike / phishing warnings (roadmap 35)

Autofill answers "may this page see this record?". It says nothing about the
danger next to it: a page bound to **no** record that is a visual twin of one that
is. `paypa1.com`, `pаypal.com` (a Cyrillic `а`), `goggle.com` — each is unbound,
so autofill offers nothing and says nothing, which is exactly when a look-alike
does its work.

5.6.0 adds a check in the trusted core that folds a hostname to a **skeleton** —
decoding punycode, stripping diacritics, mapping confusable characters to the
Latin letters they imitate, collapsing `rn`→`m` — and warns when the page's host
collides with a host the vault knows under that skeleton, or sits one edit away
from one on the same top-level domain. It never blocks; the judgement it can make
locally is *"this resembles somewhere you have an account"*, not *"this is
fraud"*.

- The **browser extension** shows a non-blocking caution before any fill,
  rendered in a **closed shadow root** so the phishing page cannot read out of the
  warning the name of the site it is imitating.
- `spm phishing-check <host>` answers the same question from the command line and
  exits non-zero when it warns.

No blocklist, no network request, and no new extension permission.

### Scoped CLI secret access (roadmap 48)

A **secret scope** is a named, least-privilege allow-list of records, stored in
the vault:

```
spm scope add ci --secret DB_PASS=42 --secret API_TOKEN=my-api:password
spm scope list
spm scope show ci
```

Each entry maps an environment-variable name to a record (by id, or a pattern
that must identify exactly one) and a field (`password`, `username`, `url` or
`notes`). A scope is the one place that says which secrets a non-interactive
caller may reach — and resolving one is the only path from a scope name to a
value. It never widens: a caller given scope `ci` reaches exactly the records
`ci` lists and no others.

### Secret injection for commands (roadmap 52)

Scopes exist to be handed to programs without writing plaintext anywhere:

```
spm run --scope ci -- ./deploy.sh          # secrets in the child's env, nowhere else
spm run --secret TOKEN=42:password -- curl ...   # ad-hoc, no stored scope
spm env --scope ci --format dotenv          # print for eval / a .env file
```

- `spm run` puts the resolved secrets in the **child process's environment** and
  nowhere else — not on disk, not on the argument vector (so nothing shows in
  `ps`) — and drops the vault lock before the child starts, so a long-running
  child does not hold it.
- `spm env` prints the same values as `export`/JSON/dotenv for `eval`, and says
  plainly on stderr that `eval` exposes them to the calling shell.

Values cross from the core to the shell **NUL-delimited**, so a secret can hold
any byte and never touches a temporary file. A scope resolves as a unit: if one
entry cannot be resolved, nothing runs.

### Shell completion (roadmap 49)

```
source <(spm completion bash)        # bash
spm completion zsh  > "${fpath[1]}/_spm"
spm completion fish > ~/.config/fish/completions/spm.fish
```

Completes the top-level verbs and the common subcommands (`scope`, `plugin`,
`record`, `ssh`, `sync`, …). Like `help`, it runs before any dependency,
language or policy prompt, so it works on a fresh platform and never emits a
banner into the script.

### Plugin SDK with capability sandboxing (roadmap 50)

A plugin is a **separate program** in `~/.config/spm/plugins/<name>/` with a
`plugin.json` manifest that declares a subset of a **closed capability set**:

| Capability | What the plugin receives / may do |
|---|---|
| `records.list` | Record summaries on stdin — labels, usernames, URLs; **never** a password |
| `secret.get` | The records of **one named scope** (roadmap 48), as `SPM_SECRET_<VAR>` |
| `password.generate` | A freshly generated password in its context |
| `clipboard.copy` | The host copies text the plugin returns |
| `notify` | The host shows a notification the plugin returns |

```
spm plugin install examples/plugins/spm-inventory
spm plugin list
spm plugin run spm-inventory
```

The design mirrors the browser native host: the plugin **never sees the vault
key**. The trusted host resolves exactly what each granted capability entitles
the plugin to and hands it over — record summaries carry labels but no secrets,
`secret.get` reaches only the records of the one scope the manifest names — and
honours a plugin's clipboard/notify requests only where the capability was
granted. Consent is explicit and **pinned to the manifest**: a plugin that later
asks for more must be granted again.

A reference plugin ships in `examples/plugins/spm-inventory/`; its `run.py`
documents the whole contract in one small program.

## Compatibility

- **No format change.** 5.6.0 stays on vault format 6. Scopes are stored like
  saved searches; nothing else about how a vault is stored or read changes.
- **Everything is opt-in.** The phishing warning never blocks; scopes, `run`/`env`
  and plugins exist only when you create them; a plugin runs only after explicit
  consent and reaches only what it was granted.

## Testing

The core suite gained tests for the look-alike check (homoglyph, swapped
character, typosquat, and the genuine and unrelated hosts it must spare) and for
secret scopes (round-trip, all-or-nothing resolution, refusal of bad variable
names, unknown fields and ambiguous patterns). The native-host regression asserts
the look-alike caution is projected to two strings and no more. The shell suite
runs `phishing-check`, a scoped `run` that injects only the named variables, `env`
projection, completion parsing and verb coverage, and the example plugin under
consent — checking that a `records.list` plugin sees labels but no secret, and
that an invalid manifest is refused.

## Upgrading

Nothing to do. Reinstall or redeploy the Dashboard; your vault is untouched.
Scopes, `run`/`env`, completion and plugins are all opt-in — create a scope or
install a plugin when you want one.
