## Read this before upgrading

**A vault saved by 3.0.0 cannot be opened by 2.13.0 or earlier.** Those
releases hand the vault file straight to GnuPG, which answers `no valid
OpenPGP data found`. The upgrade happens in place the first time a vault is
written, so it is not a step you can decline, and it is not a step you can
reverse by reinstalling an older release.

**Keep a copy of your vault and your `.recovery` file before you upgrade.**
Nothing here is expected to need them — the migration is ordered so that no
instant is unrecoverable, and `spm forgot` finishes an interrupted one — but a
backup taken before a one-way format change costs nothing, and it is the only
thing that makes the change reversible.

Everything else is compatible. No command changed its name, its arguments or
its output, and every existing vault still opens.

This is a major version because the vault format changed, not because the
feature list is long.

## Highlights

**The master password no longer encrypts the vault.** Format 3 seals the vault
under a random 256-bit *vault key*, and seals only that key under the master
password. Both live in one file, so nothing that copies, backs up, syncs or
bundles "the vault" had to change.

The consequence is the point: changing the master password rewrites a few
hundred bytes of key envelope instead of re-encrypting the whole vault, and the
vault key — the thing `.recovery` protects — stays the same across every
password change you will ever make. A recovery file therefore stops going
stale, and `spm forgot` stops depending on when it was last written.

This also removes the sharpest edge in the old design. `.recovery` used to hold
the master password itself, which made it password-equivalent and made the
*ordering* of two writes load-bearing: a vault re-encrypted while `.recovery`
still named the old password was the one state recovery could not undo. It now
holds a key that no password change invalidates.

**The vault records its own format version.** A `META_VAULT_VERSION` row,
written on every write. A vault without one predates this and is format 1;
opening and saving any vault upgrades it in place, so there is no separate
migration step and no flag day.

**One trusted core, not two implementations of it.** Every operation that
touches the vault's bytes — unwrapping the key, reading, writing, rewrapping,
stamping the version, staging and installing `.recovery`, archiving a history
generation — now lives in a single Python module. The CLI invokes it as a
subprocess and passes secrets on stdin; the SPM Dashboard imports the same
file; the browser bridge reaches it through the same wrappers.

The reason is the bug class the previous release kept producing. The CLI's
shell and the dashboard's Python each implemented the format separately, and
three call sites still handed a container straight to `gpg` — a divergence the
old byte-parity test could only detect *after* it had been written. With one
implementation there is nothing left to diverge: 343 lines of duplicated crypto
in the dashboard became a 72-line adapter that only forwards, and the
regression suite parses the dashboard's AST and fails any of those functions
that grows a body of its own.

## Changed

**Key derivation is pinned rather than inherited.** Both writers now pass
`--s2k-mode 3 --s2k-digest-algo SHA512 --s2k-count 65011712` alongside the
cipher. Measured rather than assumed: GnuPG 2.2 already defaults to s2k mode 3
at the maximum iteration count, so the concrete change is the digest, which
defaults to **SHA1**. The larger point is that these stop being whatever the
local gpg happens to do — a user's `gpg.conf` can change all of it underneath
the application, and a security parameter that is implicit can be neither
reviewed nor migrated.

**`spm.sh` is now generated from real source files.** SPM still ships as one
file; it is no longer written as one. `./build.sh` assembles it from
`src/spm_core.py`, `src/spm_web_server.py` and `src/spm.sh.in`, byte
identically, and CI fails any change where the script and its sources
disagree. Release archives now carry `src/` and `build.sh`, so anyone holding
this release can run `./build.sh --check` and confirm the `spm.sh` they were
given is exactly what those sources produce.

**`spm doctor` reports the vault's format version**, and says plainly when the
next write will upgrade it. It also distinguishes a recovery file that merely
*decrypts* from one that actually holds the current vault key, and names the
command that fixes the difference.

## Fixed

Reading a vault and reading *a file that is a vault* are now the same code
path. History snapshots, `.bak` files and synced copies are the same container
as the live vault, and three places — the CLI's `history-restore` and
`sync pull`, and the dashboard's `/history-restore` — proved a file by handing
it straight to `gpg`. Each would have refused every snapshot taken after the
format changed, with the live vault left correctly untouched.

## Not in this release

The roadmap's foundation section asked for "Argon2id where available", and
Argon2id is not available. GnuPG cannot express it — OpenPGP string-to-key is
hash-iteration by construction — and neither can the OpenSSL that current
Debian, Ubuntu and macOS actually ship, since Argon2 arrived in OpenSSL 3.2 and
`hashlib` has never offered it. Every remaining route is a third-party
dependency, which is the portability rule this project is built on.

What this release delivers instead is a KDF policy that is pinned and
inspectable rather than inherited. `ROADMAP.md` records the rest as
outstanding, alongside the data-layer replacement that will bring a memory-hard
KDF within reach.

## Upgrading

Install as usual. The first write to each vault migrates it in place; there is
no migration command to run. `spm doctor` will tell you the format version
before and after.

If a migration is interrupted, `spm forgot` completes it: it tries the
recovered secret as a vault key first and as a master password second, and the
second route opens exactly the vaults caught mid-migration. A migration whose
recovery public key is unusable refuses before anything is encrypted, leaving
the vault byte-identical and no staging files behind.

Downgrading to 2.13.0 after a vault has been written is not supported. Restore
your pre-upgrade backup instead.

## Verification

`./build.sh --check`, `bash -n`, `shellcheck -x -S warning`, `compileall` over
the core and the dashboard, and the full regression suite pass on Ubuntu,
macOS and in the official Termux container.

The trusted core carries its own 24-test suite covering container round-trip
and corruption, stamping idempotence, migration moving recovery to the key,
rewrap preserving data and recovery byte-identically, the migration crash
window, recovery failing closed with no litter, scope-id stability, snapshot
dedup and retention, the command interface's refusals, and `recover` across all
three recovery shapes. Five defects found during review were each proved by
mutation — the mutation applied, the suite confirmed to fail for the right
reason, then the fix confirmed to restore it.
