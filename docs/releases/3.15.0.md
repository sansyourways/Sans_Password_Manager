# Sans Password Manager 3.15.0

Two things: sync stops being welded to one transport, and a vault imported from
a phone can be tidied in bulk without anyone guessing on your behalf.

## Pluggable sync transports

Sync already copied the encrypted vault to a directory, with a three-way
conflict model and a pull that refused to install a remote it could not
decrypt. That logic was correct. It was also welded to `cp` and `sha256sum`
against a local path, so anything that was not a mounted filesystem could not
use it.

A transport now answers three questions and nothing else: can I reach this
target, put the remote object in this file, make this file the remote object.
Everything that decides anything stays above it, so it is identical whichever
transport you use, and a transport added later cannot skip a safety check
because it is never asked to perform one.

```bash
spm sync push  ~/Dropbox/spm                              # dir, the default
spm sync pull  backup@nas.local:/vaults    --transport rsync
spm sync status gdrive:spm                 --transport rclone
```

`dir`, `rsync` and `rclone` ship. None of them is operated by this project,
which is the constraint the roadmap set: SPM writes no credentials and creates
no accounts, and if `rsync` or `rclone` is absent the transport says so rather
than half-working. `SPM_SYNC_RSYNC_SHELL` passes rsync a different remote shell
for a non-default port, an identity file or a jump host.

Digests are measured locally, over a fetched copy, for every transport alike. A
remote-side digest is a claim, not a measurement, so none is asked for. A push
is read back and compared before the base digest records it.

### Unreachable is not empty

The one genuinely new hazard. On a filesystem, "the remote file is not there"
is a fact. Over a network it can also mean nothing could be reached, and
conflating the two turns an outage into "no remote version exists" — which is
exactly the state in which pushing over someone else's newer vault feels safe.
Every transport therefore proves it can reach the target before any decision is
taken, and a fetch that fails for any reason other than a definite absence is
fatal.

## Tidying imported entries

A vault filled by importing from a phone arrives carrying its folders as text
in the notes (`folder: Main Database`) and its service names as Android package
identifiers (`com.duolingo`, `id.go.kemensos.pelaporan`). At a few hundred
entries, fixing that by hand is not a realistic afternoon.

The Passwords page now offers to tidy them, and the offer appears only when
there is something to accept. Applying sets each entry's folder from the marker
in its own notes, renames the entry, and keeps the original identifier in the
notes as `app: com.duolingo` — once, so a second run has nothing left to add.

### It is a review, not a rewrite

Every proposed name is a text box rather than a verdict, because **no rule gets
this right in general**: the last segment of `com.lsdroid.cerberuss` is the app,
and the last segment of `com.spotify.music` is not. SPM proposes its best guess,
you correct the ones it got wrong, and unticked rows are not touched. The folder
is shown but not editable — it is read from the entry's own notes, which is not
a guess.

A record with no proposal cannot be written by the request that applies one, so
a stale review cannot change something the vault was never asked about.

## Not called sync

The button says **Tidy**, not Sync. This release also ships sync transports, and
two unrelated features sharing that word on adjacent pages would be a good way
to make somebody push a vault when they meant to rename an entry.

## Compatibility and rollback

No change to the vault format, key wrapping, the recovery file or the installer.
`spm sync push <directory>` keeps working exactly as before; `--transport dir`
is the default. Tidying is opt-in and changes nothing until applied. Revert to
v3.14.0 to go back; a tidied vault is an ordinary vault.
