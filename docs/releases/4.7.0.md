# Sans Password Manager 4.7.0

The browser session locks when you say it does — and a four-release-old
assumption gets corrected by measuring it.

## The item this closes, and how

The last open P2 item was "cheap unlock": WebAuthn in the extension popup,
reusing the ceremony the Dashboard already implements, so re-unlocking would be
a Touch ID tap instead of typing a master password. It was recorded as blocked
on a design decision rather than on code.

It is closed here without being built, because the decision was foreclosed and
the reason it existed was wrong. Both of those are measurements, not opinions.

## Why the popup cannot reuse the Dashboard's credential

A WebAuthn credential is bound to the relying-party id it was created under,
and a browser will assert one only when that id is a registrable suffix of the
calling origin. The Dashboard registers under its own domain. The popup's
origin is `chrome-extension://<id>`, which has no domain at all.

Run from the popup, with a virtual authenticator attached:

| `rp.id` | result |
| --- | --- |
| omitted | succeeds — defaults to the extension id |
| the extension's own id | succeeds |
| the Dashboard's domain | `SecurityError` |

So the security key or phone a user already enrolled for the Dashboard can
never be used by the popup. A popup ceremony would need its own enrolment under
the extension id: a second credential, a second thing to lose, and a second
unlock path — which is precisely the outcome the item was written to avoid.
There was no design decision to make. There was a platform rule nobody had
tested.

## Why the item existed at all, and why that was wrong

The browser-extension roadmap has said since 3.1.0:

> MV3 service workers are torn down aggressively. A connected native port
> extends a worker's life but does not pin it forever, so re-unlocking will
> happen more often than in a manager with a persistent background page. The
> mitigation is not a longer session — it is making unlock cheap.

That paragraph is what produced the WebAuthn item. Measured in Chromium 151,
two runs, each left completely untouched for the whole interval:

| SPM's idle setting | untouched idle | session survived | service worker |
| --- | --- | --- | --- |
| raised to 10 hours | 602 s | **yes** | still running |
| default, 300 s | 366 s | **no** | **still running** |

The worker was alive in **both** runs. The browser never tore anything down.
What ended the second session was SPM's own 300-second idle timeout — a value
readable only from `SPM_BRIDGE_IDLE_SECONDS`, an environment variable no
browser ever sets, which means it was not adjustable in practice at all.

The cost users felt was real. The cause was misattributed to the browser, and
that sent the fix looking in the wrong place for four releases.

## What shipped instead

**Lock after** is now a control in the popup: 1 minute, 5 minutes, 15 minutes,
30 minutes, 1 hour. The default is 5 minutes, exactly what it was. The choice
is remembered, and the popup shows how long the current session has left
instead of describing the lock in the future tense.

The host **clamps** what it is asked for rather than obeying or refusing it —
floor 30 seconds, ceiling one hour (`SPM_BRIDGE_IDLE_CEILING`), and never past
the absolute session cap. Refusing an out-of-range value would hand a caller a
way to map the configuration by probing it, and there is nothing to gain by
that: the honest answer to "give me twelve hours" is the ceiling.

A session keeps the terms it was unlocked with for its whole life, and an
unlock that fails changes nothing — a wrong password is not a way to move the
window for the next session.

## The trade, stated plainly

A longer idle window means the master password sits in the native host's
process memory for longer. That is the whole of what is being offered, it is
why there is a ceiling, and it is why the default did not move. Everything that
discarded the password before still discards it: **Lock SPM**, the twelve-hour
absolute cap, the native connection ending, and the browser closing.

## The boundary grew by one action

`status` returns whether a session is open, the window it was opened with, and
the seconds remaining. It is the only action that answers while locked, which
makes it the one most likely to grow a convenient extra field later — "and
which accounts would match here" is exactly the shape that gets added without
anyone noticing what it discloses. So it is projected like every other
response, onto `unlocked`, `idle` and `expires_in`, and the regression suite
asserts that a vault field offered to it does not cross.

## Testing

`tests/native_host_protocol.py` drives the host over real native-messaging
framing: the ceiling clamps, the floor clamps, a non-numeric window falls back
to the default, a failed unlock leaves both the session and the window alone,
and `status` carries no secret.

Two mutants, each killed by its own assertion:

| Mutation | Killed by |
| --- | --- |
| the clamp returns whatever it is given | the ceiling did not clamp |
| a failed unlock still applies the window | a wrong password moved the window |

The second one survived the first version of the test, which asserted that a
failed unlock left the session locked but never looked at the window it had
written. The assertion was tightened until the mutant died.

The picker's browser test needed the same treatment, and the reason is worth
recording because it is a trap rather than a typo. It asserted a fill after a
fixed 900 ms sleep. A commit runs a real vault decryption in a subprocess, so
that number was always a bet on the machine -- and when it started losing, the
failure read as "the password was not filled", which looks exactly like a
defect in the fill.

Worse was the mirror of it. The check that a *synthetic* keypress fills nothing
used the same short sleep, so with the trusted-event gate deleted the test
still passed: the fill was on its way and simply had not landed yet. A negative
assertion measured on too short a clock reports silence as success. The
positive assertions now wait for the value instead of the clock, and the
negative one waits long enough that a fill would have arrived and is followed
by a positive control on the same page -- real keys must fill, or "nothing was
filled" is not evidence of anything.

## Upgrading

Reload the extension. It gains the `storage` permission, which holds one thing:
the idle-timeout choice. No vault data and no session state are stored there.
