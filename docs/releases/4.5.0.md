# Sans Password Manager 4.5.0

Which pages may see a credential, decided in one place.

## Two rules that had no implementation

The browser-extension roadmap has carried a list of fill-path rules since
3.1.0 — the properties that separate autofill from a credential leak. Two of
them were text:

> **Refuse to fill an `http://` page from a record whose URL is `https://`.**
> Downgrade protection.

> Subdomain scope is **opt in per record**, written into the URL field.

Both ship here.

## Opt-in scope, and why it is opt in

A record's URL field may now be written as a scope:

```
https://example.com        exact host only
https://*.example.com      example.com and every host beneath it
```

The wildcard is expanded by the bridge and never inferred. That restraint is
the whole design. Without a public suffix list, "also match the parent domain"
turns a record for `foo.co.uk` into a match for everything under `.co.uk`, and
bundling a PSL is a large data dependency for a project that has none.

There is one guard that does not need a PSL, and it is a floor rather than a
substitute: `https://*.com` is refused, because nothing legitimately covers a
whole top-level domain. `*.co.uk` still parses — SPM cannot tell it from
`*.example.com`. That is the honest cost of having no PSL, and it is the reason
scope is opt in per record instead of inferred for every record.

The matching stops at a dot, which is the part worth testing. A bare suffix
comparison lets `*.example.com` match `notexample.com`, a hostname anyone can
register.

## Downgrade protection, failing closed

A record bound to an `https://` URL is refused on an `http://` page.

The list and the fill give the same answer. An account that the fill will
refuse is not offered in the picker, so nobody chooses one and is told no
without being told why.

It fails closed, and this is the part that changes behaviour for an existing
install. The refusal needs to know the page's scheme, which the extension sends
and older versions do not. A caller that does not say what the page is gets
refused for https-bound records, because an unknown scheme cannot be shown to
be secure, and a credential fill is not the place to assume the safe answer.

**Reload the extension after upgrading.** An old copy will stop filling
https-bound records until you do. That is the rule working, not a regression.

## One matcher

`bridge-list` and `bridge-get` each carried their own copy of the matching
rule, written inline in a shell heredoc. They had not yet disagreed in
behaviour, but the rule that decides whether a web page may see a credential is
the last place in this codebase to keep two implementations — and 4.4.1 had
just finished paying for exactly that mistake in the extension's fill.

Matching now lives in `src/spm_core.py`. The CLI decrypts and delegates.

## The form agrees with the bridge

A field that accepts what the feature refuses is worse than one that refuses
early. `https://*.com` used to save cleanly and then match nothing, with the
refusal arriving at fill time where there is nowhere to print it. The entry
form now names the reason, explains the scope form in all twelve languages, and
the view page renders a scope as a scope rather than as an href that cannot
resolve.

## What was verified

The rule is driven through the CLI's own bridge commands, not the matcher
alone, because the shell is where the argument order and the exit status live.
Five mutations, each killed by the assertion written for it:

| Mutation | Caught by |
|---|---|
| A bare hostname silently becomes a wildcard | a bare hostname was treated as a wildcard |
| Suffix match without the dot boundary | `*.example.com` matched `notexample.com` |
| Allow a whole-TLD scope | `*.com` was accepted as a scope |
| Drop downgrade protection | an https-bound record was offered to an http page |
| Treat an unknown scheme as secure | a missing page scheme was treated as secure |

The suite also asserts that a refusal exits non-zero, that a list stays
secret-free whatever it matches, and that every refusal the core can produce is
declared in the native host's error table — an undeclared one is projected onto
the generic refusal, which would make "this page is not secure enough" look
identical to every other failure at the moment the user most needs to tell them
apart.

## The other half of this item, and why it is not here

The roadmap pairs scoping with "cheap unlock": WebAuthn in the popup, reusing
the Dashboard's ceremony, so the master password is not typed per fill.

That is not merely unwritten. The popup reaches SPM through the native host,
which has no part in the Dashboard's WebAuthn ceremony and no session for an
assertion to attach to. Making it work is a design question about where a
verified assertion is redeemed, not an afternoon of code, and answering it
badly would put a second unlock path next to the one that already exists. Both
roadmaps record it as needing that design.

## Upgrading

No vault, format or configuration change. Reload the browser extension so the
scheme reaches the bridge; until then an old copy will refuse to fill
https-bound records.
