# Sans Password Manager 5.4.0

Four roadmap items, a "finish the security-and-lifecycle backlog" cluster. No
format change: 5.4.0 reads and writes exactly the vaults 5.3.0 does. Archive is a
new optional attributes key; the breach work adds report fields and read paths.

## What's new

### Archive state (roadmap 23)

A third record state beside favourite and trash. **Archiving** a password or
record sets it aside — gone from the default lists, counts and search — without
deleting it or putting it on a purge clock. It is independent of trash: a record
is out of the default view if it is trashed *or* archived, and each has its own
page and its own restore.

- Dashboard: an **Archive** page with unarchive, and an archive control on record
  and password rows and their detail views.
- CLI: `spm archive list`, `spm archive set <type> <id> | password <id>`, and
  `spm archive unset …`.

### Offline compromised-password database (roadmap 34)

The password breach check can now run **entirely on-device**. Point SPM at a
local dataset and it never touches the network:

```
SPM_PWNED_OFFLINE=/path/to/pwned  spm security --breaches
spm security --breaches --offline /path/to/pwned
```

The source is **auto-detected** and **source-agnostic**: a single HIBP
"ordered-by-hash" file is searched by a seek-based binary search (it is never
loaded whole), and a directory of per-prefix range files is read by prefix. The
free, keyless, k-anonymous online range API remains the opt-in fallback when no
offline source is configured.

### Account-identifier breach monitoring (roadmap 33)

A new check flags records whose **service** belongs to a known breach — the piece
the password check never covered. It matches the account's email domain and the
record's URL host against an **open breach-metadata list**: the public record of
which domains were breached and when, never any credentials.

It is **fully free and on-device**. There is no HIBP account API and no
subscription; no account identifier ever leaves the device. A small bundled list
ships as the default; extend or replace it with your own `SPM_BREACHED_DOMAINS`
file, or refresh it from a public list URL — a download that sends nothing about
your accounts:

```
spm security --account-breaches
spm security --refresh-breach-list https://example.org/breached-domains.txt
```

- Dashboard: a **Breached services** section on the Security page.

### Browser-extension vault-lock control (roadmap 38)

Already shipped; its roadmap "Open" status was stale. The extension popup's
**Lock SPM** button clears the native host's cached session, and the native-host
regression now asserts the session reads locked afterwards. Verified and marked
shipped, with no new feature code.

## Compatibility

- **No format change.** 5.4.0 stays on vault format 6. The archive attributes
  key and the new report fields are additive; a 5.3.x build still opens a 5.4.0
  vault and ignores what it does not know.
- **Fully free, nothing sent about your accounts.** No feature here requires a
  paid service or an API key. The account check runs on-device against open
  breach metadata; the offline password check reads a local dataset; the online
  password range API stays free, keyless and k-anonymous, and opt-in.

## Testing

The core suite gained an archive round-trip (set/clear, excluded from the default
walk and counts, findable, survives an unrelated edit, independent of trash), an
offline compromised-password check against both fixture layouts (a seeded and a
clean password), and account-domain matching (email domain and URL host, with a
clean domain not flagged and a user file overriding the catalogue). The shell
suite runs archive, the offline password check and the on-device account check
through the CLI. The Dashboard suite covers the Archive page and its nav entry,
the Security page's breached-services section, and accessibility for the new
controls. The native-host regression asserts the session is locked after the
extension's lock.

## Upgrading

Nothing to do. Reinstall or redeploy the Dashboard. Your vault is untouched. The
account and offline checks are opt-in and run on-device.
