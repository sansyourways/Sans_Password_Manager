# Sans Password Manager 3.4.0

Diagnostics you can script against, a dashboard that does half the work per
request, and a version comparison that was wrong on macOS.

## `doctor --json`

```bash
spm doctor --json | jq -r '.checks[] | select(.status != "ok") | .summary'
```

The same checks `spm doctor` has always run, emitted as a document rather than
a page. stdout carries the JSON and nothing else, so it needs no filtering
before `jq`, and the exit status mirrors the verdict, so a monitor can gate on
it without reading the document at all.

Each check carries a stable id — `duplicate_ids`, `empty_passwords`,
`split_records`, `vault_format`, `recovery_pubkey`, `recovery_pairing`,
`file_permissions` — so a check added in a later release does not reshape the
ones already there. Nothing in the output is a secret, and the regression suite
asserts that against both a password field and a note body rather than trusting
the intent.

The record-integrity scan moved into the trusted core on the way. It had been
an inline script inside the CLI's doctor, and the JSON report needed the same
answers; a second copy is exactly the arrangement the core exists to prevent.
Both now read one implementation, and the human output is unchanged.

## The dashboard does half the gpg work

A format-3 read is two gpg invocations: the key envelope under the master
password, then the data under that key. The envelope's answer is identical for
every request of a session, and it is the expensive half — 753ms for a full
read against 400ms for the data alone, measured here.

The dashboard now holds the unwrapped key for the life of the session:

| | gpg invocations for 5 page loads |
|---|---|
| 3.3.0 | 10 |
| 3.4.0 | 5 |

The key lives in the session record and nowhere else, so it dies with the
session at the same moment the master password does. That is deliberately not
a process-wide cache — one would survive logout — and a test now fails the
build if one appears. It is not a new class of exposure either: a session
already holds the password the key is derived from.

A cached key that no longer opens the vault is not an error. A restore or a
sync can replace the file under a live session, so the read falls back to the
master, re-derives and re-caches.

## Version ordering was wrong on macOS

`version_is_newer` compared releases with `sort -V`. That is a GNU extension:
BSD sort, and therefore macOS, has no `-V`. Where the option is missing the
command fails and the comparison reads an empty string, and where a plain sort
is substituted it orders `2.10.10` before `2.10.9` — backwards.

This is the function the auto-updater uses to decide whether a newer release
exists. It now compares dotted numeric components in POSIX awk, which agrees
with `sort -V` on every case checked and depends on nothing that varies by
platform. Reverting it fails the suite with exactly the symptom: `2.10.10`
reported as not newer than `2.10.9`.

A guard also fails the build if `sort -V`, `date -d`, `base64 -w`, `grep -P`,
`sed -i` or `mktemp -p` reappears in shipped code without a BSD fallback.

## Durability, asserted rather than assumed

The write path stages beside the vault, fsyncs, renames and fsyncs the
directory. That is only worth its complexity if it holds when a step fails, so
six tests break one step each — a full disk while staging, gpg refusing, a
crash at the rename, a truncated container, a corrupted payload, a read-only
directory. Each asserts the two properties that matter: the previous vault
still opens, and nothing is left behind in the directory.

Concurrency is asserted on the outcome. Five writers race one vault through the
CLI's own lock and all five records must survive — checking only that the vault
still opens would pass while updates were being lost. Removing the lock leaves
1 of 5.

## A gap this release found and did not close

Writing the concurrency test surfaced something the test itself then tripped
over: **macOS does not ship `flock(1)`**, so on macOS SPM runs with no advisory
vault lock at all. A CLI write and a dashboard write at the same moment can
lose one of them.

This is not new in 3.4.0 and 3.4.0 does not fix it. What changed is that it is
now stated plainly in the README and `docs/SECURITY.md`, which previously said
only "when `flock` is available" — true, but not something that tells a macOS
user they are the exception.

SPM warns at startup when it has no lock, and that is the right default; a
password manager that refuses to start is worse than one that tells you. But a
warning is not protection. On Linux, removing the lock leaves one of five
concurrent writers' records intact, which is the shape of the failure.

The test now reflects reality rather than papering over it: where `flock`
exists the race runs and every record must survive; where it does not, the
test asserts the warning instead of faking a lock and reporting a pass.

A portable lock — `mkdir` is atomic on every POSIX filesystem — is the fix, and
it is deliberately not in this release. It changes a concurrency path in a
password manager and deserves its own review rather than riding along at the
end of a batch.

## Upgrade and compatibility

No vault-format migration. Vaults, recovery material, CLI commands, the
dashboard and the browser extension are unchanged from 3.3.0.

## Verification

- Generated `spm.sh` reproduced from `src/`
- Full disposable-vault regression suite passed; core tests 24 → 34 across this
  release
- gpg invocations counted through a shim in front of the real binary, against
  the same format-3 vault, for 3.3.0 and this build
- A keyed read returns byte-identical plaintext to a master-password read; a
  legacy vault reports no key rather than raising; a wrong key is refused
  rather than returning empty plaintext
- Version comparison mutation-tested three ways, including a wrong zero-pad
  that survived the first test set and needed a case designed for it
- Fault tests mutation-tested: removing the staging cleanup fails three of
  them, writing straight to the vault fails two
- Bash syntax, ShellCheck, Python compile and the generated-source check clean
