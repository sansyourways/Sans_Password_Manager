# Sans Password Manager 4.4.1

A fill that looked like it worked.

SPM ships two browser extensions: `browser-extension-universal/`, which is the
current one, and `browser-extension/`, kept for compatibility. Both inject a
small function into the page to write a username and password into a login
form. They were supposed to inject the same one.

They did not. The universal extension wrote through the setter on
`HTMLInputElement.prototype`:

```js
const setter = Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, "value").set;
setter.call(element, value);
```

The compatibility extension wrote:

```js
el.value = v;
```

On a plain HTML form those are the same thing. On a site built with a
framework that tracks its own state they are not: the framework patches the
instance's `value` property, so a direct assignment updates what the browser
displays and leaves the framework believing the field is still empty. The
field looks filled. The user presses submit. Nothing is sent.

`browser-extension/` is packaged into every release archive, so this was in
installed copies, not only in the repository.

## Why nothing caught it

4.4.0 added a browser harness — the packed extension really loads in headless
Chromium, its service worker really starts, the id the browser assigns really
is the one `extension-id.sh` derives. It did not test the fill, and the reason
it did not is worth stating: there was no fill to test. There were two inline
functions, each written out inside a `scripting.executeScript` call, and a
test would have needed a third copy of one of them. That test would have
passed. It would have been testing itself.

So the fill became a file:

```
browser-extension/fill.js
browser-extension-universal/fill.js
```

byte-identical, loaded by both popups, and handed to `executeScript` by name.
The test drives that exact function. The regression suite `cmp`s the two files
and requires each popup to inject the shared function rather than an inline
one, so the copies cannot separate again quietly.

## The fixture matters more than the test

`tests/extension-fill.mjs` loads a login form in Chromium and asserts the fill
did what it claims: the visible username and password are filled, a hidden
honeypot and a disabled and a readonly field are not, the value arrived
through the native setter, and `input` and `change` both fired.

The first version of that fixture could not fail. The honeypot sat *after* the
real field, so deleting the visibility filter changed nothing — the correct
field was still first. And the "framework" read `element.value` when the input
event fired, which returns the right answer whichever way the value was
written. Both mutants survived.

The fixture that ships puts the honeypot first in document order and gives the
real password field an own-property `value` accessor that discards writes,
exposing what it actually received separately. Now reverting to
`element.value =` produces:

```
=== mutant 1: the legacy behaviour, element.value = value ===
KILLED
      the visible password was not filled: ""
      the fill went through the page's own value setter, so a framework that
      owns the field would have swallowed it and submitted nothing
```

which is the shipped bug, reproduced.

## Tab plumbing, and where it stops

4.4.0 listed two things the browser harness did not reach — the
native-messaging round trip and the fill — and called both "tab plumbing".
The fill is now reached. The other half has an answer that is not more work:

`chrome.action.openPopup()` does open the popup under headless Chromium, and
the popup page can be attached to and driven. What it cannot obtain is
`activeTab`. That permission is granted by a genuine user gesture on the
toolbar action, and a call synthesised through the debugger protocol is not
one; `tabs.query({active: true, currentWindow: true})` comes back with a tab
that has an id and no URL. That is a deliberate Chromium boundary and the
correct response is to record it, not to engineer around it. The popup's
hostname verification keeps its CLI-level coverage, which tests the decision
rather than the plumbing. The fill it guards is now covered in a browser.

## Upgrading

Nothing to do beyond installing. No vault, format or configuration change.
Anyone using the compatibility extension should reload it after upgrading so
the corrected fill is the one loaded.
