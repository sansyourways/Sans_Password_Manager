# Sans Password Manager 5.2.0

Five roadmap items in one release — a sharing cluster, a data-model cluster, and
a per-record protection layer. No format change: 5.2.0 reads and writes exactly
the vaults 5.1.0 does.

## What's new

### Public-key record sharing, and collections (roadmap 6 & 7)

Sharing is offline and account-free. Each vault has its own **sharing keypair**:
its public key is yours to hand out, and its private key stays inside the
encrypted vault. To send someone records, you encrypt a **collection** to their
public key, producing a share file they import into their own vault. Nothing
touches a server.

The cryptography is the emergency-access kit's, generalised: a random key seals
the body (AES-256-CTR + HMAC), and that key is wrapped to the recipient with
RSA-OAEP. A share encrypted to one vault opens only with that vault's private
key, and a wrong key or a one-byte edit fails closed.

- Dashboard: a **Sharing** page — export your key, create a share from a
  collection, import a share, and manage collections.
- CLI: `spm share pubkey`, `spm share create <recipient.pem> <collection>`,
  `spm share import <file>`, and `spm collection list|create|delete`.

### Per-record passphrase (roadmap 8)

Any record's **secret fields** can be sealed under an extra passphrase, on top of
the vault. Even with the vault unlocked, a locked record's secrets stay sealed
until the passphrase is given; its plain fields still show. The sealed blob lives
in the record's own attributes, so it travels and exports with the record as
opaque ciphertext. A wrong passphrase fails closed, and the plaintext of a locked
field is never written back into the record.

- Dashboard: a record view shows locked fields as **Locked**, with an unlock
  (reveal) prompt and a remove-the-lock control; an unlocked record offers to
  protect itself.
- CLI: `spm record lock <type> <id>` and `spm record unlock <type> <id>`.

### Custom record types (roadmap 19)

Define your own record types — a label, an icon, and a list of fields — stored in
the vault. They behave **exactly** like the built-in types across the CLI and the
Dashboard: add, list, view (with redaction), edit and export, all from the one
schema engine, which now merges the built-in and custom types. A custom type
cannot shadow a built-in one, and cannot be removed while records of it still
exist.

- Dashboard: a **Record Types** page to define and remove types.
- CLI: `spm schema list|add|remove` (fields given one per line).

### Record relationships (roadmap 25)

Link records to each other — an API token to the server it belongs to, a card to
the identity that holds it. Links show on each record, are added both ways, and
resolve to the linked record's name. They live in the record's own attributes.

- Dashboard: a **Related records** block on each record view, with add and
  remove.
- CLI: `spm link <type> <id> <target-type> <target-id>` and `spm unlink …`.

## Compatibility

- **No format change.** 5.2.0 stays on vault format 6. The sharing keypair, the
  collections and custom-schema rows, and the new per-record attributes (the
  sealed blob and the links) are all additive; a 5.1.x build still opens a 5.2.0
  vault and ignores what it does not know.
- **Sealed fields and links do not cross an export as plaintext**, and a trashed
  record is excluded from a share. The sharing private key never leaves the
  vault.

## Testing

The core suite gained round-trip tests for sharing between two synthetic vaults
(with wrong-key and tampered-file failing closed), per-record lock/unlock
(wrong passphrase fails closed, the secret never in the payload), custom-schema
add/use/remove (removal guarded, built-ins un-shadowable), relationships that
survive an unrelated edit, and collections. The Dashboard suite covers the
Sharing and Record Types pages, the new sidebar entries, a custom type flowing
through the records submenu, and a record view's locked state and related-records
block. Accessibility checks cover every new control.

## Upgrading

Nothing to do. Reinstall or redeploy the Dashboard. Your vault is untouched.
