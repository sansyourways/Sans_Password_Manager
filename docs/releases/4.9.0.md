# Sans Password Manager 4.9.0

Flags in the language picker — and the first value in this project to leave the
Basic Multilingual Plane, which broke the locale generator on the way through.

## What changed

The language picker in **SPM Dashboard** and on the **documentation site** now
shows a flag beside each language.

The flag leads and the language's own name follows it, in that order and not
the other way round. That ordering is the whole design:

- **A flag is a country and a language is not.** English is not one country.
  Arabic is not one country either. The flag is a landmark for an eye scanning
  a list of twelve, never the thing that identifies the entry.
- **The flag is the part that degrades.** A platform with no regional-indicator
  glyphs — Windows, most notably — renders `🇮🇩` as the letters "ID". That is
  survivable precisely because the name beside it is doing the work, and it is
  why the name was not replaced.

Where the locale code already names a region, the flag follows the code rather
than a judgement: `pt-br` gets 🇧🇷 and `zh-hans` gets 🇨🇳. The rest are recorded
in `locales/*.json` as a `flag` field, so the choice is reviewable and a
translator can argue with it in a pull request instead of finding it hard-coded.

## The bug this found

`flag` is the first value in this project outside the Basic Multilingual Plane,
and the locale generator could not carry it.

`tools/build-locales.py` folds `locales/*.json` into a generated region of
`src/spm_web_server.py`. It wrote every value with
`json.dumps(..., ensure_ascii=True)`, on a stated assumption:

> Every value is a string, so json.dumps output is also valid Python.

That is true up to U+FFFF and false above it. `ensure_ascii` writes an astral
character as a **surrogate pair** — `"🇬"` — which is valid JSON and,
in Python source, two lone surrogates that never combine and cannot even be
encoded to UTF-8.

The failure that produces is worth describing, because none of it points at the
cause. `locales/*.json` is correct. The generated region parses. The module
imports. `./build.sh --check` passes. And then every page carrying a language
picker raises `UnicodeEncodeError` at render time.

The region is Python, so it is now written with Python's own escaping, which
emits `\U0001f1ec` and means the character. Not `ascii()` either, which quotes
with whichever mark keeps the literal shortest — the region has been
double-quoted since it was introduced and things grep it, so re-quoting every
line would have buried one real change under four thousand cosmetic ones.

**The generator now reads back what it just wrote** and compares it to what
went in, before touching the tree. Parsing is cheap and the failure it catches
is not: the surrogate bug produced a file that imported perfectly and died on
the first page that rendered a picker.

## Testing

The flag rule is enforced in two places for two different reasons — the lint,
which is the contributor-facing gate, and the generator, which is the thing
that writes source code and must not fold a broken value into it even when
invoked directly. Both are now exercised against catalogues that are broken on
purpose: a two-letter string, a non-flag emoji, an empty value and a null.

A check nothing ever fails is a check nobody has run. Both of these passed
every run until something was handed to them that should not pass.

Five mutants, each killed by its own assertion:

| Mutation | Killed by |
| --- | --- |
| the flag is dropped from the picker | the picker serves no flag for English |
| the name is dropped, leaving only a flag | the picker dropped the language name |
| the lint accepts any flag | `"ID"` was accepted |
| the generator accepts any flag | `"ID"` was accepted |
| the generator writes surrogate pairs again | the region did not read back as written |

The last one is the regression guard for this release's own bug, and it fails
at generation time rather than at render time.

The suite also reads the flag back out of the **generated region** rather than
out of the JSON, and encodes it. That distinction is the point: the JSON looked
perfect throughout.

## Upgrading

Nothing to do. If your platform has no flag glyphs you will see two letters
where the flag would be, which is the same information in a plainer form.

Adding a language now requires a `flag` in its `meta` block. `tools/i18n-lint.py`
says so by name, and accepts a directory argument so you can check a catalogue
before it is in the tree.
