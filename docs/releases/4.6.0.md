# Sans Password Manager 4.6.0

Autofill where the login form is — and an account list the page never sees.

## The item this closes

The browser-extension roadmap has carried an in-field picker since 3.1.0, and
four releases named a target version for it and were wrong within a day each
time. It stopped naming one. What it did name was the blocker: the feature is
mostly browser behaviour, and browser behaviour that is only read rather than
run is how five defects reached earlier releases.

4.4.0 built the harness — the packed extension running under headless Chromium.
4.4.1 extended it to the fill. This release is the picker itself, and the whole
of it is driven in a browser.

## What it does

Focus a login field on a site you have accounts for. A menu opens next to it,
listing those accounts. Arrow keys move through it, Enter or a click fills,
Escape dismisses it. No record ID to remember and no master password per fill:
it draws on the session the popup already unlocks, and when that session is
locked the menu never appears at all.

## The account list is not in your page

The menu is an **iframe served from `chrome-extension://…/menu.html`**, not an
injected element.

That distinction is the feature. An injected menu — a `div`, a shadow root,
anything — lives in the page's own document, and a page that wants to know
which accounts you hold can go and read it. An iframe at another origin is a
boundary the page cannot read through, script into, or see the highlight state
of. It is what Bitwarden and 1Password do, and it is the difference between
"the page cannot see your account list" and "the page probably cannot".

The content script that anchors the menu is deliberately the least trusted part
of this: it is told **how many** accounts matched, never which. The list goes
straight from the background to the extension-origin document.

There is one thing a page can still infer, and it is worth stating rather than
leaving to be discovered: the overlay has a height, and the height follows the
number of rows up to four. A page learns roughly how many accounts you have for
it. It does not learn what they are.

## The rules that separate autofill from a credential leak

Each of these has a test that fails if the code enforcing it is removed.

**A fill requires a genuine gesture.** Opening the menu is not gated — a page
can call `focus()`, and an open menu reveals nothing. Choosing an account is
gated, on `isTrusted`: the browser sets that flag, and only for input a person
really produced. A page can dispatch a `KeyboardEvent` that is identical to
Enter in every other respect and it fills nothing. This is the anti-phishing
property; a manager that fills automatically fills a look-alike page
automatically.

**The hostname is read again at fill time.** Not carried over from when the
list was built, and never taken from the page frame's own claim about where it
is — the browser's view of the sender is the only statement about the page that
the page cannot influence.

**A cross-origin iframe is never offered the picker.** An embedded login form
from another origin is a standard credential-theft pattern. This is enforced
twice: the content script is not injected into subframes at all, and the
background refuses any request that does not come from the top-level frame.
The second layer was tested on its own, with the first disabled, because a
guard that is only ever shadowed by another guard is not known to work.

**A record the picker did not offer cannot be filled through it.** So 4.5.0's
downgrade rule holds at the fill and not only in the list: on an `http` page an
https-bound record is neither listed nor fillable, and asking for it by ID
through the menu's own channel is refused.

## What this cost in permissions

An in-field picker has to run on the pages it appears on, so the extension now
declares a content script for `http` and `https`. That is the honest price and
every password manager pays it.

What it does **not** add is as deliberate: no `tabs` permission, no
`host_permissions`, and the picker's fill does not use `scripting`. The fill
happens in the content script that is already there, and the frame's URL comes
from the browser with every message rather than from an API that would need
access to every tab. The popup path is unchanged and still needs only
`activeTab`.

`use_dynamic_url` for the menu resource was evaluated and not adopted here. It
rotates the resource URL to reduce fingerprinting, which is real; it also
changes the origin the extension would have to recognise its own menu frame by,
and Firefox's MV3 does not implement it, so it would be a Chromium-only change
to a boundary check. Worth doing deliberately, not as a side effect of this
release.

## Testing

`tests/extension-menu.mjs` drives the feature end to end in Chromium: a real
login form served over http, the real content script, the real
extension-origin iframe, the real native host, and a real vault.

That round trip is new. The popup's could never be tested this way — it depends
on `activeTab`, which Chromium grants only for a genuine gesture on the toolbar
action, and a synthesised one does not count. The roadmap recorded that as a
boundary rather than pending work, and it still is. The picker does not use
`activeTab` at all, so nothing in this test is a stand-in for the shipped path;
it *is* the shipped path.

Six mutants, each killed by the assertion written for it:

| Mutation | Killed by |
| --- | --- |
| the trusted-event gate removed | a synthetic keypress fills the form |
| the top-frame refusal removed | a cross-origin iframe is offered a picker |
| the list rendered into the page | the account list is in the page's own DOM |
| any record made choosable | the picker accepts a record it never offered |
| the fill-time hostname re-read dropped | nothing fills |
| the shadow root opened | the picker's root is reachable from the page |

One test weakness was found by that pass rather than by review, and is worth
recording. The check that the page cannot read the list originally read
`outerHTML`, which does not see into a closed shadow root — so a list rendered
into one would have passed a test that claimed to prove the opposite. Replacing
it with the actual attack, a page that patches `attachShadow` before anything
else runs, showed something better: the capture comes back empty, because a
content script runs in an isolated world with its own `Element.prototype` and
the page's patch is not the function it calls.

A flake was fixed rather than retried: an arrow key could reach the menu before
its rows had rendered, so the first keypress did nothing. The menu now holds
keys until the list exists — a real defect for anyone who types quickly, not
only for a test.

## Upgrading

Reload the extension after updating. It gains a content script, and a browser
will not start running one for an extension it already has loaded until it is
reloaded.
