# Sans Password Manager 3.5.0

A rotated credential now keeps its predecessors.

## Why this is not `history-list`

SPM already had history: `history-list` and `history-restore` work on encrypted
snapshots of the whole vault. They answer "what did everything look like last
Tuesday", and restoring one reverts every record.

That is the wrong tool for the common accident, which is rotating one password,
finding the new one does not work, and needing the old one back. Restoring a
generation to recover a single field takes everything else with it.

Per-record history answers the narrow question directly.

## Using it

```
$ spm password-history 3
Previous passwords for GitHub (ID 3), oldest first:

  1. 2026-02-11T09:14:02Z  first-secret
  2. 2026-06-03T18:40:55Z  second-secret

The current password is not shown here; use "spm get 3".
```

The dashboard shows the same list on an entry's page under **Previous
passwords**, masked, with the reveal and copy controls the current password
has. It is deliberately not labelled "History": the sidebar already has a
History item meaning vault snapshots, and two things called history on one
screen meaning different scopes is a maze.

The command is `password-history` rather than an addition to the `history-*`
family for a related reason. `history-restore` overwrites a live vault.
Overloading `history` so that an argument decides between "show me one entry's
old passwords" and "revert everything" would put a destructive operation one
ambiguity away from a read-only one.

## The four rules

Each is something a caller would otherwise get wrong, so each is enforced in
one place and tested:

- **An unchanged secret writes nothing.** Editing a note or a URL must not
  manufacture a history entry.
- **An empty predecessor is not history.** A record created empty and filled in
  later has no previous password worth keeping.
- **Deleting a record deletes its history.** Leaving old passwords behind after
  someone removes an entry is the opposite of what deleting means.
- **History is capped per record.** A credential rotated on a schedule would
  otherwise grow the vault it lives in without bound.

## Where it is recorded

At the write boundary: one function in the CLI, one in the dashboard. The CLI
has twenty-one places that edit a record and the dashboard nineteen, and
wiring each of them individually would mean the twenty-second silently does not
record history. Both boundaries compare against the plaintext this process last
read, which every edit path already has.

Two properties fall out of putting it there, and both are asserted:

- **History never reaches an export.** A plaintext CSV of the vault does not
  spill passwords the user has already replaced.
- **History is not a password.** The security score, the entry list and the
  browser extension all identify a password row by a numeric first field, so
  history rows are invisible to them by construction rather than by exclusion.

## Upgrade and compatibility

No migration. Vaults written by earlier releases gain history from their next
change onward; nothing is backfilled, because the old passwords were never
stored. A vault containing history rows still opens in 3.4.x — every write path
there preserves rows it does not recognise — though those releases will not
display them.
