# Sans Password Manager 3.10.0

SPM now records what was done to your vault, so you can notice what you did not
do.

```bash
spm events
```

```text
WHEN (UTC)             EVENT    OUTCOME  DETAIL
2026-08-30T02:28:05Z   unlock   fail     reason=bad-master, scope=live
2026-08-30T02:28:06Z   unlock   fail     reason=bad-master, scope=live
2026-08-30T02:28:33Z   write    ok       records=11, scope=live
```

The dashboard shows the same log under **Tools → Security Events**, with failed
attempts called out above the table.

## Where it lives, and why that is the hard part

The log sits *outside* the vault, in plaintext, at
`~/.local/share/spm/events/<id>.log` with mode `0600`.

Inside the vault would be encrypted and tidier. It is also the wrong answer: a
failed unlock is exactly the event most worth recording, and exactly the one
that cannot be written into a vault nobody could open. A log that goes quiet
precisely when someone is guessing at your master password is not a security
log.

Putting it outside is only defensible if it carries nothing worth reading. So
it carries a time, what kind of operation it was, whether it succeeded, and a
detail drawn from a fixed vocabulary — a record count, or a reason such as
`bad-master`. No record names, no usernames, no URLs, no passwords, not even
the vault's own path.

The vocabulary is enforced rather than documented. Details are `key=value` with
both sides validated, and a key outside the permitted set raises. Free text is
how a label ends up in a log one day: someone adds a helpful "which record" to
an error path and nobody notices it is now on disk in the clear. This makes
that a test failure instead of a leak.

Someone who can read this file can already see the vault file beside it and its
modification time, so *"this vault was opened at these times"* is not new
information to them. Anything beyond that would be.

## Repeated successes collapse; failures never do

The dashboard reads the vault on nearly every page view. The first version of
this page showed 61 events, of which 56 were routine unlocks, and the five
failed attempts were buried in the middle of them. A log you cannot scan does
not do its job.

Identical *successful* events within 60 seconds are now recorded once. Failures
are always recorded individually, whatever the window says — a burst of failed
unlocks is the signal the whole feature exists for, and collapsing five
attempts into one would be the log understating the one thing it is for.

Both are adjustable: `SPM_EVENT_COALESCE` (seconds, `0` to record everything)
and `SPM_EVENT_RETENTION` (lines kept, default 500).

## It answers when the vault will not open

`spm events` reads a file beside the vault. It takes no lock, opens no vault
and asks for no master password. That is deliberate: the moment you most want
to know how many failed attempts have happened is the moment the vault is not
opening, and a command that needed the vault open could not tell you.

## Recorded at the boundary

Events are recorded inside the core's own read and write paths, not at the
twenty-odd CLI and dashboard call sites that reach them — the same choice made
for per-record history in 3.5.0, for the same reason: a path added next year
cannot forget to log.

That choice immediately found a real gap. The core writes events against
`SPM_VAULT_PATH`; the dashboard sets it, and the CLI never had, so every CLI
unlock and write went unrecorded and the log described only half the product.
Fixed at the single point where the shell invokes the core.

## Compatibility

No vault format change and no migration. The log is created on first use and an
absent one simply reports nothing. A log that cannot be written — a read-only
directory, a full disk — never fails the vault operation it describes; losing a
line is a nuisance, losing the write it describes is data loss.
