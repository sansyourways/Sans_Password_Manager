# Sans Password Manager 3.9.0

You can now check where a release came from, not just that it arrived intact.

## The gap

`install.sh` downloaded the archive and its `.sha256` from the same host and
compared them. That is a transfer check. It says nothing about origin: whoever
can write one of those files can write the other, and the installer would have
reported success either way.

## What changed

Every release archive now carries a **build attestation** — a signed statement,
recorded in Sigstore's public transparency log, that this exact archive was
produced by this repository's release workflow. `spm.sh` is attested alongside
it, because that is the file people actually run; a copy lifted out of a
release can be verified on its own.

The installer checks it before installing anything:

```text
Provenance  : attestation verified against sansyourways/Sans_Password_Manager
```

It needs the GitHub CLI 2.49 or newer, signed in. When it cannot check, it
says which reason applies rather than staying quiet — a silent skip reads as a
successful check:

```text
Provenance  : not checked (the GitHub CLI is not installed)
Provenance  : not checked (this GitHub CLI is too old; needs 2.49+)
Provenance  : not checked (the GitHub CLI is not signed in)
Provenance  : 3.8.0 predates build attestations; checksum only
```

A release at or after 3.9.0 that *fails* verification aborts the install.

Two of those lines exist because of specific mistakes worth avoiding. Debian
stable ships gh 2.23, which has no `attestation` command at all; reading that
as a forged archive would refuse an install for a reason that has nothing to do
with the archive. And releases before 3.9.0 genuinely have nothing to verify,
so treating them as failures would break installs that were fine when they were
made.

## Reproducible archives

The archive is built by `release-archive.sh`, which the suite runs too, so what
produces a release is what was tested. It is deterministic: entry order is
sorted, every timestamp comes from the commit rather than the clock, and the
uid, gid and extended-timestamp fields zip normally records are stripped.

The same commit rebuilt anywhere gives the same bytes, which is what makes the
published checksum something you can independently arrive at:

```bash
git checkout v3.9.0
./release-archive.sh
sha256sum -c Sans_Password_Manager_v3.9.0.zip.sha256
```

Outside a git checkout, set `SOURCE_DATE_EPOCH` to the commit's timestamp.

## On testing this

Building the archive twice on one machine and comparing proves nothing: the two
are identical whether or not the sort, the timestamp normalisation or the field
stripping are done at all. Five mutants covering exactly those defences
survived that test. The invariants are asserted against the zip directly
instead — sorted order, every timestamp equal to the commit's, no extra fields,
no leftovers, and the files needed for `./build.sh --check` to run from an
unpacked release.

The installer's absent-gh case had the same shape of hole: this machine has a
real gh in `/usr/bin`, so a test that put a stub directory *first* on PATH was
exercising the signed-out branch and never the missing-gh one. The stub PATH
now carries only bash and awk.

## What this is not

This ties a release to a workflow in a repository. It does not tie it to a key
a person holds — hardware-backed signing is a separate item and still open.
Nor does `spm` check its own provenance after installation; the check happens
once, at install time.

## Compatibility

No vault format change, no migration. `spm.sh` gains nothing but a version
string; the change is in how a release is built, published and verified.
