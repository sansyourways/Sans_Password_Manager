# Sans Password Manager 3.14.0

Recovery no longer has to rest on one file and one private key staying
simultaneously available and secret.

## Split recovery

`spm shares split` divides the vault key into `n` shares over GF(2**8) with a
threshold `t`. Any `t` of them reconstruct the key; any `t - 1` reveal nothing
at all — not "nothing practical", nothing: Shamir's guarantee is
information-theoretic, not computational.

```bash
spm shares split                          # 3 of 5, the default
spm shares split --threshold 2 --shares 4
spm shares status
spm shares combine
```

A share is a single transcribable line carrying its format, the threshold,
which share it is, which set it belongs to, the payload, and a checksum.

## Three decisions

**What is split is the vault key, not the RSA private key.** The vault key is
stable: `rewrap` changes only the master-password envelope around it. Shares
written on paper therefore keep working after any number of password changes,
which is the only thing that makes writing them down sensible. Splitting the
private key instead would have kept the RSA dependency and produced shares
that go stale.

**Every share carries a checksum over its own text.** Shamir has no integrity
of its own. Combine three shares with one character wrong and you get a
different key, silently, with nothing to say which share was at fault — the
only symptom being a vault that will not open. The checksum turns that into a
refusal naming the share.

**The share format carries no digest of the secret.** Reconstruction is proved
by opening the vault instead. A digest would verify a combine offline, which is
precisely why it must not exist: it is the one thing an attacker holding
`t - 1` shares could attack without the vault.

## What it does not do

`t` shares are equivalent to the vault key: together they open the vault
without the master password. That is the same power the recovery file and its
private key already have as a pair. Split recovery changes how many pieces must
be gathered, not what they are worth once gathered.

Minting a new set does not revoke an old one, because the vault key does not
change. `spm shares split` says so and asks before replacing the recorded set;
destroying superseded shares is the holder's job.

Minting is CLI-only. At threshold the shares are the vault, and rendering them
through a browser would put them in a page, a scrollback and possibly a proxy
log on the way to the person meant to write them down.

## Doctor

The vault records that a set exists — identifier, threshold, count, date — and
never a share. `spm doctor` reports it, and reports a **failure** when a vault
has neither a usable recovery file nor a share set: the one state with no way
back, which neither check could see on its own.

## Compatibility and rollback

No change to the vault format, the key wrapping, the recovery file or the
installer. `META_RECOVERY_SHARES` is a metadata row that older builds already
skip along with every other `META_` row. Existing vaults are untouched until
`spm shares split` is run. Revert to v3.13.0 to go back; a vault that has been
split keeps working, and its recorded set row is simply ignored.
