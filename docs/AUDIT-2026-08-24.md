# Combined bug audit — Sans Password Manager

**Date:** 24 August 2026
**Source under audit:** `spm.sh` at `VERSION="2.10.11"` (tag `v2.10.11`, commit `7b86b50`)
**Deployment under audit:** PM2 app `spm-web` serving `https://spm.sansyourways.xyz/`

This merges two audits that were run separately and never reconciled:

- **Source review** — *SPM 2.10.10 · Deep Bug Audit*, 14 findings against snapshot
  `1dba3cd`, since updated in place to record 2.10.11 remediation. Held at
  `Silent-Nexus/docs/harness-design/spm-deep-bug-audit-2026-08-24.html`
  (untracked; exists only on this host). Findings keep their original `F-nn` IDs.
- **Live deployment review** — run against the running system. New findings are
  numbered `D-n`.

The two disagree on what is fixed, and the disagreement is the point of this
document. The source review's remediation claims are correct **about the source
tree**. They are not true of the vault that is actually serving traffic.

## 3. Open findings

### D-1 — 2.10.11 is installed but not deployed (High)

`spm.sh` and `/usr/local/bin/spm` are both 2.10.11 and byte-identical. The
running web server is not.

```
$ curl -s https://spm.sansyourways.xyz/login | grep -oE 'v2\.10\.[0-9]+'
v2.10.10

$ pm2 jlist | … spm-web  online  SPM_VERSION=2.10.10  bind=0.0.0.0  port=8777

$ ls -la ~/.local/share/spm/spm_web_server.py
-rw-r--r-- 1 Sans Sans 213988 Aug 24 00:38 spm_web_server.py   # pre-dates 7b86b50 (01:49)
```

Marker comparison — repository source versus the script actually executing:

| Marker | `spm.sh` | running `.py` |
|--------|---------:|--------------:|
| `ipaddress.ip_address` | 3 | 1 |
| `auth_lock` | 4 | **0** |
| `_sweep_login_failures_locked` | 3 | **0** |
| `X-Real-IP` | 2 | **0** |

PM2 executes the *generated* `spm_web_server.py`, which `write_spm_web_script`
emits from `spm.sh`. Updating `spm.sh` and restarting PM2 leaves the old Python
running. Here even the version string is honest, because `SPM_VERSION` was never
re-passed — but that is luck, not design: the usual presentation of this bug is a
correct version banner in front of stale code.

**Consequence.** F-04 and F-05 are marked remediated in the source report and are
live on the published vault. The running `_login_client()` is still:

```python
def _login_client(self):
    try:
        return self.client_address[0]
    except (AttributeError, IndexError):
        return "unknown"
```

Behind nginx that is always `127.0.0.1`, so `login_failures` holds one key for
every proxied visitor. With `LOGIN_MAX_FAILURES = 5` and
`LOGIN_LOCKOUT_SECONDS = 60`, five wrong passwords lock out *everyone* for sixty
seconds, repeatable indefinitely at no cost. Reproduced on a throwaway vault:
after five failures the correct password is refused with "Too many … Try again",
and the log reads `failed login from 127.0.0.1`.

The 2.10.11 source fix is correct, and correct in the way that matters — the
header is trusted only when the socket peer is loopback, so a direct network
client cannot choose its own throttle key:

```python
if peer.is_loopback:
    forwarded = (self.headers.get("X-Real-IP", "") or "").strip()
    try:
        return str(ipaddress.ip_address(forwarded)) if forwarded else str(peer)
    except ValueError:
        return str(peer)
return str(peer)
```

That distinction matters here specifically because the vault also listens on
`0.0.0.0` (D-2). Trusting the header unconditionally would have been worse than
the bug it fixes.

**Fix:** the full deploy sequence, not a restart.

1. install the new `spm.sh` (already done)
2. regenerate: source a copy of the installed script with its last line stripped, then call `write_spm_web_script`
3. `pm2 restart spm-web --update-env` with `SPM_VERSION=2.10.11` set explicitly
4. `pm2 save`
5. assert a 2.10.11 marker is present in the regenerated `.py` — `grep -c auth_lock` must be non-zero

### D-2 — A plain-HTTP route bypasses TLS (High)

```
$ sudo ufw status numbered | grep 8777
[37] 8777/tcp        ALLOW IN    Anywhere
[73] 8777/tcp (v6)   ALLOW IN    Anywhere (v6)

$ ss -ltnp | grep 8777
LISTEN 0 5 0.0.0.0:8777 0.0.0.0:*  users:(("python3",pid=943789,fd=4))

$ curl -s http://127.0.0.1:8777/login | grep -oE 'type="password"'
type="password"
```

The master-password form is served unencrypted in parallel with the HTTPS path,
reaching the same vault. There are **two** rules, not one — the IPv6 rule `[73]`
was missed by the earlier pass, which named only `[37]`.

Remote exposure was accepted when plain HTTP was the only option; that decision
pre-dates the domain feature. SPM did not open the port —
`configure_firewall_for_web()` only prints advice.

**Fix:** restart the PM2 app with `SPM_WEB_BIND=127.0.0.1`, then
`sudo ufw delete 73 && sudo ufw delete 37` — **higher number first**, because ufw
renumbers after each delete. This changes how the vault is reached, so confirm
before doing it. Best combined with the D-1 restart, since both need the same
`pm2 restart --update-env`.

### F-10 — Blank backup-code edit erases all codes (High; the report says Low)

The `/backup-codes-edit` handler encodes whatever the textarea submitted, empty
included:

```python
encoded = base64.b64encode(codes.encode("utf-8")).decode("ascii")
```

There is no blank-preserve branch. The passphrase handler 250 lines earlier
received exactly that guard in 2.10.11, as the F-01 fix:

```python
if not secret:
    try:
        secret = base64.b64decode(existing_secret.encode("ascii"), validate=True).decode("utf-8", errors="strict")
    except Exception:
        self.send_error(500, "Stored passphrase cannot be decoded; vault was not changed")
        return
```

Backup codes never got it. **This is the same defect class as F-01 — which was
rated High and fixed — with a worse payload.** A passphrase is typically
recoverable from the service that issued it; recovery codes are not recoverable
from anything, which is their entire purpose. A blank submit destroys them
silently and returns HTTP 302 success.

**Fix:** apply the F-01 pattern to `/backup-codes-edit` — reuse the stored value
when the field is blank, and fail closed when the stored value cannot be decoded.
Do the same audit sweep across every edit route so the blank-field contract is
defined once rather than per-handler; the source report's own P2 item asks for
this.

### D-3 — Stale firewall rules for a decommissioned service (Medium)

`code-review-report-8097.html` (tracked, commit `7f4a94c`, SPM 2.8.2, 10 Aug)
records in its own footer how it was published:

> VPS report URL: `http://5.104.81.199:8097/code-review-report-8097.html` … UFW allowing `8097/tcp`

The server is gone; the rules were never withdrawn:

```
$ sudo ufw status numbered | grep 8097
[36] 8097/tcp        ALLOW IN    Anywhere
[72] 8097/tcp (v6)   ALLOW IN    Anywhere (v6)

$ ss -ltnp | grep 8097
(nothing listening)
```

Two ports open to the internet with nothing accountable behind them. Unlike D-2
this involves no trade-off — nothing is served there, so deleting the rules
changes no behaviour.

**Fix:** `sudo ufw delete 72 && sudo ufw delete 36` (higher first). Separately,
decide whether `code-review-report-8097.html` stays in the repository as history;
it is five releases stale and all three of its findings are already closed.

### F-12 — Editor commands containing arguments do not work (Low)

`spm.sh:84` reads `EDITOR_CMD="${EDITOR:-nano}"` and `spm.sh:1648` invokes
`"$EDITOR_CMD" "$tmp"`, so the whole value is treated as one executable name.
`EDITOR="code --wait"` — a common configuration — fails despite being valid.

**Fix:** split the value into an array with `read -ra`, or invoke through the
shell only after validating the value.

### F-13 — Local agent state is not excluded from Git (Low)

`.nexus/` and `SansBACKUP_DEC_25/` are both untracked and both un-ignored:

```
$ git check-ignore -v .nexus SansBACKUP_DEC_25
(no output — neither is ignored)
```

Nothing has been committed by accident, but the ignore rules do not prevent it.

**Fix:** add both to `.gitignore`.

### D-4 — Temporary diagnostics still in place (Low)

```
/etc/nginx/sites-available/spm.sansyourways.xyz:1:  log_format spm_origin '… origin="$http_origin" ua="$http_user_agent" -> $status';
/etc/nginx/sites-available/spm.sansyourways.xyz:36: access_log /var/log/nginx/spm-origin.log spm_origin;

-rw-r--r-- 1 root root 55058 Aug 24 21:23 /var/log/nginx/spm-origin.log   # 311 lines
```

Added to read the real `Origin` header from the iPhone rather than guess at it,
and it did its job — the evidence in §4 comes from this log. It now records

**Fix:** restore `/tmp/spm-vhost.bak` over the vhost, `nginx -t`, reload, remove
the log. Move the backup out of `/tmp` first if it is worth keeping.

`git diff --check v2.10.6..HEAD` still reports trailing whitespace at
`docs/SECURITY.md:147`. No runtime effect; it shows the check is not enforced in

**Fix:** strip it and add `git diff --check` to CI.

### The 2.10.9 → 2.10.10 sequence

The CSRF fix in 2.10.9 repaired Safari omitting `Origin` on same-origin form
posts, and in the same change broke the iOS Home Screen web app, which sends
`Origin: null`. Both are Safari; only one was tested. 2.10.10 distinguishes an
*opaque* origin from a *foreign* one:

```python
# "null" is an opaque origin, not a foreign one: iOS home-screen web
# apps send it for their own same-origin form posts.
if origin and origin.lower() != "null":
    return self._same_origin_post()
```

**Confirmed live** from the D-4 origin log — the failing request and the fixed
one, both with `Origin: null`, on either side of the deploy:

```
line  6: POST /add origin="null" ua="… iPhone OS 18_7 … Safari/604.1"  -> 403
line 34: POST /add origin="null" ua="… iPad CPU OS 26_6_0 …"           -> 302
```

Three `POST /login origin="null"` requests also return `302`. The write path is
proven end-to-end against a real opaque-origin client. Note the post-fix success
came from an iPad; the iPhone has since browsed the vault normally
(`/passphrases`, `/notes`, `/generator` all `200`) but has not re-submitted an
entry, so the original reporter's own device is not independently confirmed.

## 5. Verified sound

Examined and found correct. Do not re-investigate without a reason.

- **Vault writes are serialised.** `do_POST` holds an in-process `RLock` *and* an
  `flock` across processes, spanning the whole read-modify-write rather than just
  the final replace.
- **Vault content is escaped.** A record named `<img src=x onerror=…>` renders
  inert, and an embedded `<form method="post">` does not pick up a CSRF token —
  worth checking, because the token is injected by regex over the response.
- **CSRF tokens cannot be cached or replayed.** Pages are `no-store`; a token from
  another session is refused; a foreign `Origin` is refused whatever token the
  body carries.
- **Secret files are locked down.** Vault, Cloudflare credentials and the `sp-sec`
  store are `0600`; their directories are `0700`.
- **Certificate renewal is unattended.** `certbot renew --dry-run` succeeds via
  `dns-cloudflare`, independent of any CDN setting. The vault certificate is valid
  to 21 Nov 2026.
- **Static analysis is clean.** `shellcheck -x -S warning` passes. Remaining
  style-level hits are deliberate, such as the literal `$host` inside generated
  nginx configuration.
- **Source-review coverage** (from the 2.10.10 report): `bash -n` pass, ShellCheck
  pass, full regression suite pass across all 20 import/export formats, generated
  Web server and native host compile, release ZIP inspected at 67 entries with no
  `.bak` copies or agent state included.

## 7. Standing notes for later sessions

- **Regenerate, don't just restart.** PM2 executes the generated Python. This trap
  has now produced a false "the fix didn't work" twice; D-1 is its third
  appearance, and the first where it silently invalidated an audit's remediation
  claims.
- **A source audit is not a deployment audit.** The 2.10.10 report's "Not claimed"
  section is explicit — no firewall rule changed, no live certificate requested.
  Everything in the `D-n` series sits in that gap. Re-run the live checks after
  any release that claims to remediate a runtime finding.
- **The iPhone Home Screen web app is the release target**, not an edge case. It
  behaves unlike a browser tab in ways local `curl` never shows. Before tagging
  anything that touches auth, CSRF, cookies, caching or headers, enumerate the
  client cases explicitly: absent `Origin`, `Origin: null`, matching origin,
  foreign origin.
- **When a live request is the only source of truth**, add temporary
  `$http_origin` logging to the vhost and read the real header — then take it out
  again (D-4).
- **The source report lives outside this repo**, untracked, in the Silent-Nexus
  tree. If it matters, move it in; otherwise treat this document as the record.

## 8. Full codebase sweep

A third pass over all 11,626 lines of `spm.sh`, plus `install.sh` and the test
suite, looking for defects the first two audits did not cover. Static gates were
re-confirmed clean first: `bash -n` passes on all three scripts, and
`shellcheck -x -S warning` is silent (the 23 remaining hits are all
style-level — 18 are `SC2016`, single-quoted `$host` and `$http_origin` inside
generated nginx config, which is correct as written).

Every finding below was reproduced, not inferred.

### S-1 — Import silently corrupts non-UTF-8 source files (High)

Every reader in the import path opens with `errors="ignore"`:

```python
with open(src_path, "r", encoding="utf-8", errors="ignore", newline="") as f:
```

A CSV exported from a Windows password manager is commonly cp1252, not UTF-8.
Each non-ASCII byte is silently dropped. Run through the production importer
extracted verbatim from `spm.sh`:

```
$ python3 importer.py csv win2.csv vault2.txt
(importer reported SUCCESS)

$ cut -f4 vault2.txt          # the stored password
dummy-pw-Gre
  expected: dummy-pw-Größe
```

`Café Münchén` stored as `Caf Mnchn`, `josé` as `jos`. **The importer reports
success.** The user discovers it when a login fails — by which time the source
export may be gone.

*Fix:* decode strictly and fail with a clear message naming the offending line,
or sniff the encoding and transcode. `errors="ignore"` is never right for
credential data; at minimum use `errors="strict"` and catch.

### S-2 — Eight line-break characters erase records (High)

`_vf()` guards the record format by stripping separators:

```python
return str(value or "").replace("\t", " ").replace("\r", " ").replace("\n", " ")
```

It handles three characters. Python's `str.splitlines()` — used by every parser
to read the vault back — splits on **eleven**. The other eight pass the
sanitiser untouched:

```
0x0b  0x0c  0x1c  0x1d  0x1e  0x85  0x2028  0x2029
```

A label containing U+2028 (ordinary in text copied from a web page) is written
as one record and read back as two:

```
record written as ONE line: '1\tMy Bank\talice\tdummy-pw\tnotes\t2026-01-01\n'
len(splitlines()) on read : 2
  line 0: '1\tMy'                                          fields=2
  line 1: 'Bank\talice\tdummy-pw\tnotes\t2026-01-01'       fields=5
```

`parse_entries` requires ≥6 fields, so it discards both halves — **the entry
disappears from the vault** and the next write persists its absence.

The failure is asymmetric and therefore especially confusing: Bash reads the
vault with `read -r`, which splits only on `\n`, so an entry added from the CLI
still lists correctly in the CLI while being invisible in Web Mode.

*Fix:* strip on the same set `splitlines()` splits on, or stop using
`splitlines()` and split explicitly on `\n`.

### S-3 — A predictable temp registry makes SPM shred arbitrary files (High, local)

`spm.sh:26` fixes the cleanup registry at a guessable path in a world-writable
directory:

```bash
SPM_TMP_REGISTRY="${TMPDIR:-/tmp}/.spm_tmpreg.$$"
```

It is created by append (`>>`), with no `O_EXCL`, and `chmod 600` runs *after*
the first write. `cleanup()` then reads that file on every exit and calls
`secure_wipe` — which is `shred -u` — on every path it lists.

A local attacker who pre-creates `/tmp/.spm_tmpreg.<pid>` therefore chooses
which files SPM destroys, with the victim's privileges. `/tmp` is `drwxrwxrwt`
and `pid_max` is 4194304 here, so pre-creating the whole space is cheap.
Demonstrated by replaying `cleanup()`'s own loop against a planted registry:

```
victim exists before: YES
victim exists after : NO — shredded
```

This needs a local attacker on a shared machine; on a single-user host it is not
exploitable. It is listed High because the primitive is arbitrary file
destruction, including the vault itself.

*Fix:* create the registry with `mktemp` like every other temp file, or hold the
list in a shell array and never write it to disk.

### S-4 — Import silently discards unrecognised record types (Medium)

The dispatch loop counts only rows whose `type` it recognises, and errors only
when *nothing* matched:

```python
if added == 0:
    raise ValueError("No supported records found in import.")
```

Four rows in, one stored, success reported:

```
$ python3 importer.py csv mixed.csv vault3.txt
(reported SUCCESS)
rows in source: 4    rows imported: 1
```

Types like `login`, `credential` and `card` — all common in third-party
exports — vanish without a word.

*Fix:* report `added` and `skipped` counts, and list the unrecognised type
values so the user can remap them.

### S-5 — Web Mode writes create no history snapshot (Medium)

`archive_current_vault()` keeps 20 encrypted generations and backs
`spm history-list` / `history-restore`. It is called from three places, all in
Bash. The Python `encrypt_vault()` writes only `.bak` — the only "history"
references after line 5986 are a comment and the two CLI dispatch entries.

So every change made from the iPhone — the primary client — leaves no history
entry, and `history-restore` cannot reach it. The single `.bak` generation rolls
forward on the next write.

This compounds F-10 directly: destroy backup codes from Web Mode, save anything
else afterwards, and the codes are gone from both `.bak` and history.

*Fix:* call the same archival logic from the Python write path.

### S-6 — No `fsync` on any vault write (Medium)

`grep -n 'fsync' spm.sh` returns nothing. Both writers stage to a temp file and
rename — `os.replace()` in Python, `mv -f` in Bash — with no durability barrier
on the file or its directory. A crash or power loss between the rename and the
writeback can leave a truncated or zero-length vault.

*Fix:* `os.fsync()` the temp file before `os.replace`, then fsync the directory;
`sync` the staging file on the Bash side.

### S-7 — `spm update` never reports "already latest" (Low)

Two functions parse the same field, and only one strips the tag prefix:

| Function | Regex | Result |
|---|---|---|
| `autoupdate_latest_tag` (3080) | `"tag_name": *"v?([^"]+)"` | `2.10.11` |
| `cmd_update` (3189) | `"tag_name": *"([^"]+)"` | `v2.10.11` |

`cmd_update` then tests `[ "$latest_tag" = "$VERSION" ]` — comparing `v2.10.11`
against `2.10.11`, which can never match. Verified against the live API while
running the matching release: the auto-update path correctly stays silent, and
`spm update` offers to download and reinstall the version already installed.

*Fix:* add `v?` to the `cmd_update` regex, or compare with `version_is_newer`,
which already exists.

### S-8 — Update temp-dir fallback is a predictable path (Low)

```bash
if ! tmpdir="$(mktemp -d "${TMPDIR:-/tmp}/spm_update.XXXXXX" 2>/dev/null)"; then
    tmpdir="${TMPDIR:-/tmp}/spm_update.$$"
    mkdir -p "$tmpdir"
fi
```

`mkdir -p` succeeds on a directory that already exists, so if `mktemp -d` fails
the release ZIP is downloaded into, and extracted from, a directory an attacker
may own. The checksum is verified against the downloaded ZIP, which does not
help once the extraction directory is attacker-controlled.

*Fix:* delete the fallback and fail. If `mktemp -d` is unavailable, refusing to
self-update is the correct outcome.

### S-9 — CSP allows inline script (Low)

The baseline header is otherwise strong — `object-src 'none'`, `base-uri
'none'`, `frame-ancestors 'none'`, `form-action 'self'` — but carries
`script-src 'self' 'unsafe-inline'`. Vault content is escaped, so this is
defence-in-depth rather than a live hole.

### Checked and sound in this sweep

- **No path traversal surface.** No filesystem path in the web server is built
  from request input; every `Location` header is a constant except one, which is
  `urllib.parse.quote`d.
- **CORS is correctly scoped** to `http://127.0.0.1:<port>` and
  `http://localhost:<port>` with the exact runtime port — not a wildcard, and
  credentials are only allowed for those two origins.
- **Update integrity fails closed.** A missing checksum asset aborts the update;
  the digest is compared before extraction, not after.
- **Vault history retention is bounded** at 20 generations, pruned by mtime.
- **Record parsers are tag-safe.** A label that begins with `PASSPHRASE`,
  `AUTH`, `NOTE` or `BACKUP_CODE` cannot be confused for a record of that type,
  because the parsers match on the tag *plus* a tab.
- **Authenticator edits are lossless.** `/authenticator-edit` reuses the raw
  stored Base32 when the field is blank, rather than a decoded round-trip — the
  pattern the other edit routes should follow.
